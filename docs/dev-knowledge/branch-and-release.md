# 分支、版本号与正式版维护策略

本文说明齿轮盛宴（Create-Delight-Remake）的**版本号含义**、**子版本产品阶段**，以及 Git 分支（`main` / `release-vxxxx`）与正式版后对 **CDC / CDC mixin**、**HotAI** 的约束。发布操作步骤见 `.agents/skills/release/SKILL.md`；人工入口见 [development.md](../development.md#版本发布流程)。

## 版本号含义

当前版本号格式：

```text
v0.{主版本}.{子版本}.{更新编号}
```

示例：`v0.5.0.16` → 主版本 `5`、子版本 `0`、更新编号 `16`。同一「子版本线」写作 `0.5.0.x`。

发布脚本（`release-plan.ps1`）按四段 `vA.B.C.D` 解析；其中 `A.B.C`（如 `0.5.0`）对应一条子版本线，并推导维护分支名 `release-v$A$B$C`x（如 `release-v050x`）。

## 更新节奏

以每个假期（寒暑假、节假日）**开始前几天**为节点，发布一个**新子版本的正式版**。自 `0.4.7.x` 起，每个子版本都按下一节的阶段推进。

## 子版本阶段（产品视角）

自 `0.4.7.x` 起，每个子版本依次经历：

| 阶段 | 做什么 | 渠道与补丁 |
|---|---|---|
| **测试版-功能更新** | 快速、频繁加功能：加/更新 mod、自创多方块、自创机制等 | 仅 GitHub；**无**更新补丁 |
| **抢先预览版-准备发布** | 正式版前的**最后一个测试版**，通常在正式版前 **2–3 周**发布。以此为分界，**之后不再做功能更新** | 仅 GitHub；**无**更新补丁 |
| **正式版** | 基于抢先预览版反馈：修 bug、调不合理数值、任务书勘误后，在假期前发布 | 正式渠道；此后维护更新带补丁 |
| **正式版-持续维护** | 下一子版本正式版发布前：稳定且易复现的崩溃、严重影响正常流程的问题、其他确有必要的更新；同一子版本下正式版存档一般可无损升级 | 每次维护更新都有补丁 |
| **正式版-停止维护** | **下一子版本正式版**发布后转入；制作组不再处理该版本 bug 反馈、不提供排查（社区频道仍可能有玩家帮忙） | — |

### 与发布工具的对应（勿硬套名称）

release skill / 脚本只有两类 GitHub Release：**正式**（非 prerelease）与 **测试**（prerelease，tag 常带 `-test`）。仓库**没有**单独的「抢先预览」Release 类型或脚本开关。

- **测试版-功能更新**、**抢先预览版**：都是产品阶段；发布时通常仍走「测试 / prerelease」。抢先预览 = 正式版前最后一个测试包这一产品节点，不是第三种 `ReleaseType`。
- **正式版** 及之后的 **持续维护** 更新：走「正式 / 非 prerelease」Release。
- 测试与抢先预览「无更新补丁」与脚本行为一致：测试版 Release 说明写明不提供 Patch，需下完整包。

## 分支角色

| 分支 | 角色 | 典型改动 |
|---|---|---|
| `main` | 主要开发分支 | 持续合入功能与修复；可 bump CDC，因此可带入依赖新 CDC 载荷的 mixin 修复 |
| `release-vxxxx` | 某一子版本正式稳定线的维护分支 | 尽可能不做功能性更新；正式版发布后以 bug 修复为主 |

命名与 `release-plan.ps1` 一致：未指定 `-TargetBranch` 时推导 `release-v$A$B$C`x；分支存在则用之，否则回退 `main`。历史例：`release-v045x` … `release-v048x`、`release-v050x`。

## 阶段与分支 / CDC 如何对齐

不必把每个产品阶段钉死在唯一 Git 分支上；常见对应如下：

1. **测试版-功能更新**  
   主要在 `main`（或尚未切出的开发）上快速合入功能；可更新 CDC。

2. **接近正式、进入抢先预览前后**  
   常切出或落在 `release-vxxxx`；以抢先预览为分界后**不再功能更新**。CDC 是否已冻结仍以「该子版本是否已有正式（非 prerelease）Release」为准——抢先预览本身仍是测试包，不单独等于 CDC 冻结。

3. **正式版发布之后 → 正式版-持续维护**  
   - 非必要禁止功能更新，只做上表范围内的维护。  
   - **CDC 版本冻结**：不能再 bump CDC / 合入依赖新 CDC 构建的 mixin。  
   - **仍可**加入 HotAI 形式修复（不依赖换 CDC jar）。  
   - KubeJS / 配置等不换 CDC 的修复可以，但仍避免非必要功能向改动。

4. **下一子版本正式版发布 → 本线正式版-停止维护**  
   制作组不再跟该子版本反馈；需要 CDC mixin 的修复应落在 `main` / 新子版本线，而不是回灌已停止维护、且曾冻结 CDC 的旧 `release-vxxxx`。

## CDC mixin 与 HotAI

| 手段 | `main` / 未冻结 CDC 的开发 | 已正式发布、处于持续维护且 CDC 已冻结的 `release-vxxxx` |
|---|---|---|
| 更新 CDC 并加入/修改 CDC mixin | 可以 | **不可以** |
| HotAI（`.badiff` 等） | 可以 | **可以** |
| 不依赖换 CDC jar 的修复 | 可以 | 可以（范围见持续维护） |

判断「CDC 是否已冻结」：该子版本是否已有 **正式（非 prerelease）Release**。脚本亦以 prerelease 标记区分正式/测试，不以 tag 是否带 `-test` 单独推断。

## 与当前正式线（`0.5.0.x` / `release-v050x`）

- 当前正式线为 `0.5.0.x`（`release-v050x`），处于**正式版-持续维护**（以仓库 tag / GitHub latest 为准，如 `v0.5.0.16`）。
- 该线 CDC 固定在 **2.2.16j** 一代；持续维护期间**不会**再 bump CDC，故无法合入「必须换新 CDC jar」的 mixin。
- `main` 上已有的 CDC mixin（如 ExtendedAE 胶带白名单启动空指针）预期随 **下一子版本正式线**（版本号大于 `0.5.0`，预期 `0.5.1.x`）进入正式包，而不是 `0.5.0.x` 的维护补丁。
- 维护分支急需等价修复时评估 **HotAI**，不要在 `release-v050x` 上强行升级 CDC。

条目见 [compatibility-patches.md](compatibility-patches.md)「ExtendedAE 胶带白名单启动空指针」。

## 给代理与维护者的短约束

- 知识库默认 PR 合入 **`main`**；勿默认镜像到 `release-v050x`，除非用户要求。
- 在 `release-vxxxx` 上修 bug 前确认是否需要新 CDC；若需要，改走 `main` / 下一子版本，或可行时用 HotAI。
- 玩家侧临时缓解（如改用 Java 17）可写 FAQ / 反馈回复；本页是开发与发布策略，不替代玩家文档。
- 对外描述阶段时用上表产品名称；对内跑发布脚本时只用「正式 / 测试」，不要发明「抢先预览」专用 ReleaseType。
