# 标准组件构形模块系统设计

本文记录一种基于现有标准组件的可切换放置系统。玩家手持构形模块时，可以按住 Create 工具箱菜单键（默认左 `Alt`）打开径向构形轮盘，指向目标后松开按键完成切换；右键后放置对应的真实方块，并按形态消耗构形量。

本文同时记录设计边界与当前实现状态。物品名称、构形量数值和模式成本仍可在生存测试后调整；已实现内容以文末“当前实现状态”为准。

## 设计结论

- 系统名称暂定为“构形模块”；物品显示名可以继续使用“混沌物·传动”等更有世界观色彩的名称。
- 当前版本注册传动、结构、流体、控制和物流五类构形模块；模式池由数据包显式白名单驱动。
- 模块本体为不可堆叠的可充填工具，标准组件负责补充构形量；不制作需要长期占用多个物品栏的一次性构形物堆栈。
- 所有模式放置时只消耗构形量；高价值方块和机器通过显著提高点数体现材料成本与便利溢价。
- 标准组件只用于制作模块和补充构形量，不作为每次放置时的附加物品。
- 放置后生成原模组的真实方块，挖掘时遵循原方块掉落；方块不能直接还原成构形量，避免无损跨物品转换。
- 原版和模组原有配方全部保留。构形模块提供便携施工和临场选择，直接批量合成仍应拥有更高材料效率。
- 正式架构采用“CDC 稳定底层＋KubeJS/数据包定义内容”：CDC 负责物品行为、输入、网络、放置和数据加载，整合包负责模式、成本、配方、语言、模型与任务。

## 架构定案

纯 KubeJS 只适合作为交互原型，不作为正式实现。正式版本必须保证径向菜单、模式快照和网络选择由服务端校验，目标方块通过原生 `BlockItem` 流程放置，并且充填配方不会复制或丢失 NBT；这些稳定性责任统一交给 CDC。

| 层级 | 负责内容 | 变更方式 |
|---|---|---|
| CDC 注册层 | 注册构形模块物品、自定义充填配方序列化器和必要的网络消息 | 新增物品类型或配方能力时重新构建 CDC |
| CDC 客户端层 | 复用 Create 工具箱键、径向构形轮盘、模式提示和服务端选择请求 | 输入协议或核心 UI 行为变化时重新构建 CDC |
| CDC 服务端层 | 模式校验、构形量、自动充填、权限检查、原生方块放置和原子消耗 | 新增底层规则或特殊放置策略时重新构建 CDC |
| CDC 数据层 | 加载、合并、校验和同步构形模块与模式数据 | 通用数据格式由 CDC 维护 |
| KubeJS 数据包层 | 定义模式、目标方块、构形量成本、排序、等级和放置策略 ID | 数据包重载即可调整普通模式 |
| KubeJS 配方层 | 模块本体配方、标准组件充填配方和阶段平衡 | 服务端脚本或配方重载即可调整 |
| KubeJS 资源与任务层 | 中文/英文名称、模型、纹理、说明、JEI 信息和 FTB Quests 引导 | 资源或任务重载后生效 |
| RenderJS 可选层 | 额外动画与装饰性视觉增强 | 不承担输入、同步和放置正确性；径向轮盘、固定本体图标、GUI 目标角标、构形量条和幽灵预览由 CDC 提供 |

CDC 必须在没有 RenderJS 的情况下保持完整功能；RenderJS 只能增加表现，不能成为构形模块可用性的硬依赖。

## 设计目标

- 减少大型工厂建设时转轴、齿轮、管道、机壳和控制元件对快捷栏与背包空间的占用。
- 让玩家通过一个稳定的输入方式快速切换同类方块，减少打开背包和 JEI 的频率。
- 让现有安山结构、传动、铜质流体、密封接头、黄铜控制和逻辑组件获得持续使用场景。
- 保留机械动力中不同结构、传动、流体和机器零件的成本差异。
- 让直接合成、自动化量产和构形模块分别承担“材料效率”“批量生产”和“现场施工便利”三种职责。
- 使用显式白名单和数据驱动模式表扩展附属模组，不自动把整个物品标签转化为可放置内容。

## 非目标

- 不制作一份材料可以免费变成任意机器的万能物品。
- 不允许转轴、大齿轮、齿轮箱和机器在拆除后无损互相转换。
- 不用构形模块替代原有配方、任务教学、自动化产线或仓储物流。
- 不在第一版处理传送带、轨道、软管滑轮、动力结构、成对放置方块或复杂方块实体。
- 不在第一版支持携带机器库存、流体、过滤器、频率、红石配置或其他方块实体 NBT。
- 不通过客户端单方面修改物品模式、构形量或消耗结果。

## 与现有标准组件的关系

现有组件已经形成可直接复用的职责划分：

| 标准组件 | 当前职责 | 构形系统用途 |
|---|---|---|
| `createdelight:andesite_structure_component` | 基础框架和安山机器主体 | 结构构形模块、机器主体成本 |
| `createdelight:kinetic_transmission_component` | 旋转与运动机构 | 传动构形模块充填、基础机器传动成本 |
| `createdelight:copper_fluid_component` | 铜质流体设备主体 | 流体构形模块主体与充填 |
| `createdelight:sealed_joint_component` | 密封、活动接口和流体连接 | 流体模块外壳、高级流体形态成本 |
| `createdelight:brass_control_component` | 黄铜精密控制 | 控制构形模块和精密机器成本 |
| `createdelight:logic_component` | 打包、库存与物流网络 | 物流构形模块和网络设备成本 |

构形系统不建立新的平行材料等级。标准组件决定模块属于哪个工程领域，并通过充填配方间接决定该领域构形量的材料价值。

## 玩家操作循环

1. 玩家完成对应工程阶段，制作某一类构形模块。
2. 玩家使用标准组件为模块补充构形量。
3. 手持模块时，按住 Create 工具箱菜单键打开构形轮盘，指向目标后松开按键切换当前模式。
4. 物品角标和提示显示当前形态、构形量与单次消耗。
5. 玩家右键方块表面，模块按照目标方块原本的放置规则确定朝向和位置。
6. 放置成功后由服务端扣除构形量；构形量不足且背包中有充填组件时自动充填并结算，放置失败时不消耗。
7. 放下的目标是原模组真实方块，后续连接、旋转、应力、流体和挖掘行为保持原样。

## 输入与界面

### 默认操作

- 按住 Create 的“打开附近工具箱”按键（默认左 `Alt`）打开径向构形轮盘。
- 移动鼠标指向外圈目标，松开按键或左键点击后确认；未指向任何目标时松开不会改变模式。
- 玩家在 Create 按键设置中改绑工具箱键后，构形轮盘自动沿用同一按键，不再注册独立冲突按键。
- 手持构形模块时构形轮盘优先于附近工具箱；未手持模块时 Create 工具箱行为保持不变。
- 服务端保存并验证最终模式；客户端只读取服务端写入物品 NBT 的完整模式快照来绘制轮盘。

### 显示信息

物品提示至少显示：

- 当前模式及目标物品 ID。
- 当前构形量和最大构形量。
- 放置一次需要的构形量。
- `按住工具箱键打开构形轮盘` 的操作说明。

模块在手持、掉落和第三人称中始终显示固定的二维本体图标；物品栏与快捷栏右上角使用 `8×8` 小角标显示当前目标，避免把箱子、机器等目标方块直接当成整件手持模型，也避免遮挡底部构形量条。

轮盘中央显示模块本体，外圈显示所有数据包白名单目标；当前模式使用金色标记，指向模式时显示名称与构形量费用。当前最多八个模式可以沿用单圈布局；未来超过十二个模式时再增加分页或双圈布局。

## 构形量模型

### 基本规则

- 每个模块最大构形量暂定为 `64`。
- 模块不可堆叠，物品耐久条位置显示剩余构形量比例。
- 创建模块时自带一次对应组件的充填量。
- 补充配方必须保留模块的模式、构形量与数据版本。
- 构形量到达上限后不能继续补充；配方不得静默吞掉溢出部分。
- 创造模式不消耗构形量，但仍由服务端验证模式和放置结果。

### 便利溢价

构形模块不能比直接配方便宜。设计目标为：

- 批量制造某一种固定方块时，直接配方或自动化产线最省材料。
- 临时需要多种同类方块时，构形模块用额外成本换取快捷栏空间和选择自由。
- 初始数值按约 `20%` 至 `50%` 的便利溢价设计，之后根据生存测试调整。

传动组件当前由转轴、齿轮、安山合金和铁锭合成，每次产出两个。第一版采用“一枚传动组件补充四点传动构形量”的保守换算，避免构形模块反过来成为更高效的转轴或齿轮生产配方。

## 模块配方草案

构形模块本体优先使用锻造台制作，与现有“组件作为模板、主体作为基础、特征零件作为附加”的机器配方语言保持一致。

| 模块 | 模板槽 | 基础槽 | 附加槽 | 初始构形量 | 推荐解锁 |
|---|---|---|---|---:|---|
| 传动构形模块 | 传动组件 | 安山机壳 | 电子管 | 4 | 安山时代后期 |
| 结构构形模块 | 安山结构组件 | 安山机壳 | 强力胶 | 4 | 安山时代后期 |
| 流体构形模块 | 铜质流体组件 | 铜机壳 | 密封接头组件 | 8 | 完成基础流体教学后 |
| 控制构形模块 | 黄铜控制组件 | 黄铜机壳 | 精密构件 | 4 | 黄铜与精密构件阶段 |
| 物流构形模块 | 逻辑组件 | 黄铜机壳 | `create:transmitter` | 4 | 打包与库存网络阶段 |

显示名可以使用：

- `混沌物·传动`
- `混沌物·结构`
- `混沌物·流体`
- `混沌物·控制`
- `混沌物·物流`

内部注册名建议保持工程语义，例如：

- `createdelightcore:kinetic_configuration_module`
- `createdelightcore:structural_configuration_module`
- `createdelightcore:fluid_configuration_module`
- `createdelightcore:control_configuration_module`
- `createdelightcore:logistics_configuration_module`

### 充填配方

| 模块 | 充填材料 | 补充量 |
|---|---|---:|
| 传动构形模块 | 传动组件 ×1 | 4 |
| 结构构形模块 | 安山结构组件 ×1 | 4 |
| 流体构形模块 | 铜质流体组件 ×1＋密封接头组件 ×1 | 8 |
| 控制构形模块 | 黄铜控制组件 ×1 | 4 |
| 物流构形模块 | 逻辑组件 ×1 | 4 |

充填需要自定义配方逻辑，不能使用会丢失或复制 NBT 的普通静态产物配方。第一版只要求手动充填；Create 部署器或其他自动充填应在自定义配方能够可靠复制模块 NBT 后再接入。

## 机器施工模块边界

未来若加入更多机器施工模式，应遵守以下规则：

- 模块本体只负责选择目标机器和执行放置，放置成本仍只使用构形量。
- 机器价格按其原配方、阶段和现场施工便利折算为高点数，并通过对应模块的充填组件间接结算材料。
- 高价模式可以一次触发多次自动充填；服务端先确认背包内充填组件足够，再在成功放置后原子扣除。
- 现场施工每次只放置一台机器。即使原锻造台或序列装配配方一次产出两台，施工模式也不获得双倍产量；额外成本是现场选择和免工作台组装的便利溢价。
- 第一版机器白名单只能包含空状态机器，不能复制或迁移库存、流体、过滤器、频率、配方卡或所有者数据。

因此机器施工模块是后期施工工具，不是新的机器量产路线。玩家要批量生产机器时，仍应使用现有锻造台和序列装配配方。

## 数据与实现边界

### CDC 底层职责

CDC 负责所有不能依赖脚本时序或客户端可信状态的部分：

- 通过 `CreateDelightCore.REGISTRATE` 注册构形模块物品。
- 复用 Create `AllKeys.TOOLBELT` 按键打开径向轮盘，并在手持构形模块时抑制同一次输入打开附近工具箱。
- 将当前模块所有可用模式写入物品 NBT 快照，客户端据此绘制轮盘；选择消息携带稳定模式 ID，服务端再次按白名单校验。
- 在服务端验证当前手持物、模式、等级、构形量、自动充填可用性、玩家权限和目标位置。
- 使用目标 `BlockItem` 的原生放置流程处理朝向、水含状态、放置音效、邻居更新和方块放置事件。
- 在放置成功后扣除构形量，并在需要时原子扣除自动充填组件；失败时保持物品与世界不变。
- 实现保留模块 NBT 的自定义充填配方，并拒绝超过最大构形量的输入。
- 加载、校验、合并并同步数据包中的模块与模式定义。
- 提供可扩展的放置策略边界；当前 `block_item` 使用原生 `BlockItem.place`，并动态委托 Create/Catnip 已注册的 `PlacementHelper` 实现幽灵预览、状态变换和末端延伸。通用委托要求 helper 在客户端和服务端都注册相同逻辑；仅客户端预览、自有网络协议、多点选取或长度结算仍需 CDC 增加专用策略。

实际实现时应在独立 CDC 源码仓库中完成 Java 改动；父整合包只在 CDC 版本发布后同步子模块指针、Packwiz JAR 和元数据，不直接在父仓库镜像中开发。

### KubeJS 与数据包职责

KubeJS 和 `kubejs/data/` 负责所有应该由整合包快速调平或扩展的内容：

- 每个模块允许哪些模式、默认模式、显示顺序和所需等级。
- 每个模式的目标方块、构形量成本和 CDC 放置策略 ID。
- 模块本体和充填配方使用哪些标准组件、产量与阶段材料。
- 模式对应的语言、模型、纹理、提示、JEI 说明和任务书入口。
- 依赖附属模组或配置开关的模式是否通过数据条件启用。

KubeJS 不直接监听按键或绘制轮盘，不修改玩家快捷栏槽位，不手工 `setBlock` 模拟原生放置，也不根据客户端传来的目标方块 ID 扣费或放置。

### 模块物品数据

建议保存以下字段：

```text
Mode: 当前模式 ID
AvailableModes: 当前模块可用模式、目标与成本的客户端快照
Charge: 当前构形量
Tier: 模块等级或升级状态
DataVersion: 数据版本
```

模式使用稳定字符串 ID，不使用列表下标作为持久化值。调整模式排序时，旧物品仍能解析到原模式；模式被移除时回退到该模块的第一个有效模式。

### 数据资源划分

建议使用两类可重载数据资源：

```text
kubejs/data/createdelightcore/configuration_modules/<module>.json
kubejs/data/createdelightcore/configuration_module_modes/<mode>.json
```

模块定义负责容量和默认行为，例如：

```json
{
  "item": "createdelightcore:kinetic_configuration_module",
  "max_charge": 64,
  "default_mode": "createdelight:shaft",
  "fallback_mode": "createdelight:shaft"
}
```

每个模式使用独立资源 ID，便于其他数据包逐项覆盖或禁用，而不必复制整张模式数组。例如 `kubejs/data/createdelightcore/configuration_module_modes/shaft.json`：

```json
{
  "module": "createdelightcore:kinetic_configuration_module",
  "target": "create:shaft",
  "charge_cost": 1,
  "required_tier": 0,
  "sort_index": 10,
  "placement": "createdelightcore:block_item"
}
```

模式的持久化 ID 使用数据资源 ID，例如 `createdelight:shaft`，不使用目标方块 ID 或数组下标。这样可以在不改变玩家物品 NBT 的情况下替换目标、价格或放置策略。

### 数据驱动模式表字段

每个模式至少声明：

```text
module: 所属模块
target: 目标物品或方块 ID
chargeCost: 构形量消耗
requiredTier: 所需模块等级
placementPolicy: 放置策略
sortIndex: 客户端切换顺序
```

模式表必须使用显式条目，不直接读取大范围物品标签。第三方模组更新或配置禁用目标方块时，该模式应在数据加载阶段被过滤并给出明确日志。充填配方中的 `ingredients` 仍支持物品、标签和数量，它们只负责补充构形量，不是模式放置的附加材料。

### 数据加载与同步

- 服务端数据包重载时重新建立有效模块与模式快照。
- 无效目标、未知模块、负数消耗、未知放置策略和缺失默认模式应产生明确错误；单个附属模式无效时不应令整个模块或服务器崩溃。
- 玩家登录和数据包重载后，服务端会刷新玩家背包内所有模块的模式快照，并通过原版容器槽位同步发送客户端；维度切换沿用玩家物品栈同步。
- 客户端只使用物品 NBT 快照渲染名称、目标图标、成本和预览，不能以本地数据决定实际放置结果。
- 当前物品保存的模式被删除或禁用时，服务端回退到模块定义的有效默认模式，并写回物品 NBT。
- 普通模式和成本变化应只需要数据包重载；新增模块物品、NBT 结构、网络协议、自定义配方能力或放置策略仍需要更新 CDC。

### 放置流程

1. 客户端按住 Create 工具箱键打开径向轮盘，指向目标并松开后发送稳定模式 ID。
2. 服务端确认玩家主手仍为对应模块，验证目标模式属于允许列表，再更新物品 NBT。
3. 右键时服务端预检查构形量、必要的自动充填材料、目标位置、玩家权限和方块是否可放置。
4. 普通位置调用目标 `BlockItem.place`；若目标物品与点击状态命中已注册的 Create/Catnip `PlacementHelper`，则复用其偏移和状态变换执行辅助放置。
5. 仅在放置返回成功后扣除构形量；若本次使用自动充填，同时扣除对应充填组件。
6. 客户端从服务端同步后的物品栈和世界状态刷新预览。

当前只支持单方块 `BlockItem` 施工。通用路径主动绕过目标物品用于调频、复制配置等非施工 `useOn` 交互，避免物流连接器点击已有网络时误扣费；拥有多阶段交互、成对放置、长度计算或必须由专用网络包初始化的目标，仍需专用放置策略后才能加入。

## 防套利与兼容规则

- 构形模块不能作为普通配方中的任意目标方块替代品。
- 放置方块掉落其自身，不返还构形量；构形量只能由规定的标准组件充填。
- 不提供目标方块到构形量的无损逆向配方。
- 如果未来提供拆解回收，回收效率必须低于直接制造，并按目标方块的原材料族返回组件或残片。
- 自动充填材料必须由服务端预检查并在成功放置后原子扣除；材料不足时不得先放置后回滚。
- 切换模式不改变构形量，也不允许通过 NBT 合并、铁砧、磨石或修复配方复制充填量。
- 模块不允许进入机械动力动态结构库存后自动放置，除非后续为部署器和蓝图炮建立明确兼容规则。
- 模式白名单只加入已针对当前安装版本验证的方块；相同标签或相似名称不是兼容证据。

## 解锁阶段

| 阶段 | 开放内容 | 设计目的 |
|---|---|---|
| 安山时代前半 | 原有转轴、齿轮和机壳配方 | 让玩家学习应力传递、齿轮变速和基础放置 |
| 安山时代后半 | 传动构形模块第一版、结构构形模块 | 开始建设成规模工厂时减少快捷栏负担 |
| 铜质流体教学后 | 流体构形模块 | 玩家已经理解管道、泵和流体方向后提供施工便利 |
| 黄铜与精密构件阶段 | 控制模块、传动高级模式 | 让模式切换与精密控制形成阶段升级 |
| 打包与库存网络阶段 | 物流构形模块 | 服务中心仓库和大型物流网络建设 |
| 中后期大型工厂 | 机器施工模块候选 | 方便复制成熟产线，以高构形量保留材料成本与便利溢价 |
| 终局候选 | 多模块统一构形核心 | 仅合并操作入口，不合并不同组件的成本账户 |

构形模块属于便利解锁，不应成为原方块的硬门槛。玩家在获得模块前仍能通过原配方制作全部对应方块。

## 实施阶段

### 第一阶段：传动原型（已实现）

- 在 CDC 注册传动构形模块、径向输入、网络消息、`block_item` 放置策略和自定义充填配方。
- 在 CDC 实现模式数据加载、登录/重载同步和无效模式回退。
- 在 KubeJS 数据包定义转轴、小齿轮和大齿轮三种模式。
- 在 KubeJS 配方中定义模块本体配方和四点一批的传动组件充填配方。
- 使用固定二维模块本体图标，并由 CDC 在物品栏/快捷栏右上角叠加当前目标角标；原版物品条显示构形量。
- 只验证普通手持放置，不接入部署器、蓝图炮或动态结构。

### 第二阶段：成本与自动充填（已实现，待游戏内回归）

- 按目标价值提高构形量成本，不为单次放置加入附加物品。
- 加入齿轮箱、离合器、反转齿轮箱和链式传动件。
- 验证自动充填检查、放置成功和消耗的原子性。

### 第三阶段：结构与流体（已实现，待游戏内回归）

- 加入结构和流体构形模块。
- 验证管道连接、水含状态、泵朝向和黄铜模式阶段锁。
- 将第一批模块加入“机动机器标准组件”之后的任务书说明。

### 第四阶段：控制与物流（已实现基础白名单，待游戏内回归）

- 加入精密传动、控制和物流模式。
- 对配置可禁用或依赖附属模组的目标做数据加载过滤。
- 评估模式数超过十二个后的轮盘分页或双圈布局。

### 第五阶段：机器施工候选（仅完成少量安全白名单）

- 只选择少量无初始 NBT 的基础机器验证。
- 以高构形量成本表达机器原料与施工便利溢价。
- 与现有锻造台、序列装配产量比较，确保施工模式始终存在便利溢价。

当前物流模块只将打包机、库存连接器和红石请求器作为空状态施工白名单。CDC 使用 `BlockItem.place` 而不是转发这些物品的调频 `useOn`，因此模块不会携带或复制网络 UUID、请求内容与方块实体 NBT。传送带、轨道、软管滑轮、动力结构以及需要两点或多阶段交互的机器仍明确不在通用白名单内。

## 当前实现状态（2026-08-04）

CDC 仍保持 `2.2.16g`，现已注册传动、结构、流体、控制和物流五类模块，共由 KubeJS 数据包定义 27 个模式。底层复用 Create 工具箱菜单键打开 Steam ’n’ Rails 风格的径向构形轮盘，支持稳定模式 ID、服务端完整模式快照、松键/点击选择、默认/回退模式、登录/重载时背包快照刷新、固定模块本体图标、GUI 当前目标角标、构形量条、目标 ID/单次费用提示，以及 Create/Catnip `PlacementHelper` 的动态委托；只要后续目标物品和点击状态命中已注册 helper，数据包新增模式即可自动获得相同的幽灵预测和末端延伸。

放置结算使用目标 `BlockItem.place` 或 helper 的状态变换，只在服务端确认成功后扣除构形量。模式不再声明或消耗附加材料；构形量不足时会从匹配的动态充填配方选择可用方案，预留一项或多项充填材料，并在成功放置后统一充填和扣费。手动充填拒绝超过容量的输入，物流连接器等带非施工 `useOn` 的物品不会通过模块复制频率或配置。

KubeJS 已定义五类模块的锻造配方、单材料或多材料充填配方、27 个显式白名单模式、固定本体模型、双语文本和任务书说明。模式成本完全由构形量表达，当前范围为 1 至 16 点；传动高级模式、结构底盘、流体管泵阀、精密控制、基础物流与三种空状态物流机器均已进入数据层。传送带、轨道、多点施工和通用机器自动导入仍未开放。

CDC 编译与 27 个模式的静态 JSON 校验已通过；固定本体＋目标角标、高成本模式和无附加材料结算仍需完成 JAR 构建、部署及客户端重启后的实机回归。改绑输入、幽灵延伸、各类朝向、自动充填、掉落与应力网络也仍不得标记为运行时通过。

## 第一版验收标准

- 手持模块时按住工具箱键能稳定打开轮盘，指向目标松键后切换，快捷栏选中槽不会变化。
- 客户端连续快速滚动后，服务端模式、客户端提示和实际放置结果一致。
- 放置转轴、小齿轮和大齿轮时沿用原方块的朝向与放置限制。
- 构形量不足、目标位置无效或玩家无权限时不放置、不扣费。
- 生存模式成功放置后只扣除规定构形量；创造模式不扣费。
- 充填配方保留模式和数据版本，不允许复制构形量或吞掉溢出组件。
- 放置后的方块参与原 Create 应力网络，挖掘时掉落原方块。
- 原转轴、齿轮和标准组件配方不被移除或替换。
- JEI、任务书和中英文提示明确说明模块是便利施工工具，而不是更高效的生产路线。
- 静态代码、数据和构建验证不等同于游戏内验证；完成客户端重启后的放置、联机同步和应力网络回归后，才能标记运行时通过。

## 待原型确认的问题

- “混沌物”是否作为正式显示名，还是仅保留给终局统一模块。
- 当前使用五类标准组件纹理作为固定本体，并在 GUI 右上角叠加目标角标；后续若制作专用模块纹理，只替换本体资源，不改变角标和放置逻辑。
- 当前使用自定义工作台充填配方和背包自动充填；部署器或专用充填设备仍需确认自动化是否会正确保留模块 NBT。
- 当前最大构形量统一采用 `64`，后续只根据生存回归调整。
- 服务器可以通过数据包覆盖、禁用或调整普通模式与构形量成本；新增物品类型和特殊放置策略仍需更新 CDC。
- 终局统一模块是否有足够价值；如果分类模块已经易于携带，则不必强行合并。
