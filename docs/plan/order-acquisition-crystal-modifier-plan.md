# 订单获取与订单修饰系统计划

本文记录一种参考 Vault Hunters 3 宝库水晶修饰思路的订单获取方案。核心目标不是复制宝库系统，而是把本包当前“拍卖行随机刷新未开封订单”的入口，改造成一个可被玩家逐步控制、可与自动化生产线配合的“订单构筑”系统。

## 设计目标

- 订单获取不能长期只依赖拍卖行随机盲盒。
- 玩家应能把订单导向自己已经建设的产线，例如茶、甜品、快餐、酒类或怪物餐。
- 可控性需要付出成本，不能让玩家无风险稳定刷最高收益订单。
- 订单自动化后，玩家应能获得稳定订单来源，而不是一直手动等拍卖行。
- 当前 `createdelight:unopened_order -> 右键生成 createdelight:order` 的流程应保留，并作为新系统的基础。

## 当前状态与问题

当前入口已经从单纯拍卖行盲盒推进到“随机订单 + 稳定购买 + 基础构筑”并存：

- 任务奖励给 `createdelight:unopened_order`，并额外给入门菜单印章。
- Lightman's Currency 拍卖行每半天刷新 1-3 个 `createdelight:unopened_order`。
- LC 订单商会商店出售未开封订单和基础印章。
- 玩家可以直接右键 `createdelight:unopened_order` 开封，也可以先用 `createdelight:order_seal` 写入方向。
- MBD2 `createdelight:order_builder` 已作为第一版订单构筑台，使用事件脚本处理草稿和印章。
- 完成订单后会记录玩家近期交付的顾客和品类，后续同方向订单会受到轻微软性的市场饱和金币折扣。

仍然存在的问题：

- 当前构筑台主要是右键交互，缺少清晰 UI、预览和失败反馈。
- 印章只能表达基础顾客/菜单方向，还没有催化剂、不稳定度和重签章。
- 订单来源仍然缺少后期常驻合同，不能完全承担持续自动化供货。
- 市场饱和只影响生成时金币倍率，尚未接入更完整的公告板或合同市场。

## 核心概念

### 订单草稿

`createdelight:unopened_order` 改为“订单草稿”的基础载体。它仍然可以直接右键打开，但也可以先经过工作台修饰。

概念 NBT：

```js
{
  OrderDraft: {
    Seed: 123456789,
    Seals: ["customer_human", "category_drink"],
    Catalysts: ["bulk", "premium"],
    Modifiers: ["bulk_order", "quality_request"],
    Instability: 15,
    Revision: 2
  }
}
```

当前实际落地的基础 NBT 更轻量：

```js
{
  OrderDraft: {
    Revision: 1,
    customerSeal: "human",
    categorySeal: "drink"
  }
}
```

当前使用 `customerSeal` 和 `categorySeal`，每个草稿最多保存一个顾客方向和一个菜单方向。后续催化剂、不稳定度、重签章和 seed 预览再扩展到概念 NBT。

说明：

- `Seed` 决定随机结果，方便同一草稿在预览和开封时保持一致。
- `Seals` 是玩家明确指定的订单方向。
- `Catalysts` 是输入过的修饰道具记录。
- `Modifiers` 是最终应用到订单生成上的效果。
- `Instability` 表示订单不稳定度，越高越容易出现负面修饰或失败。
- `Revision` 便于后续版本兼容旧 NBT。

### 订单印章

订单印章用于决定订单大方向，相当于“这个订单属于谁、偏向什么菜单”。

实现上不需要为每一种印章注册独立物品。第一版使用一个 `createdelight:order_seal`，通过 `OrderSeal` NBT 区分人类、精灵、饮品、甜品等方向；具体方向配置放在 `kubejs/startup_scripts/custom/order/data.js`。

第一批建议：

| 印章 | 作用 | 解锁建议 |
|---|---|---|
| 人类商会印章 | 提高人类顾客权重 | 声望 1 |
| 精灵茶会印章 | 提高精灵顾客权重 | 声望 2 |
| 矮人酒馆印章 | 提高矮人顾客权重 | 声望 2 |
| 怪物餐馆印章 | 提高怪物顾客权重 | 声望 3 |
| 饮品菜单印章 | 提高茶、果汁、酒、咖啡权重 | 声望 2 |
| 甜品菜单印章 | 提高蛋糕、派、冰淇淋、果冻权重 | 声望 2 |
| 主食菜单印章 | 提高面包、米饭、面条、饺子权重 | 声望 3 |
| 宴席菜单印章 | 提高多条目、高数量订单权重 | 声望 4 |

规则建议：

- 一个草稿最多有 1 个顾客印章和 1 个菜单印章。
- 低级印章只改变权重，不完全锁定结果。
- 高级印章可以更接近锁定，但需要更高声望或更高费用。

### 订单催化剂

订单催化剂用于给草稿添加收益、风险或限制。它应该让玩家有“谈条件”的感觉。

正面修饰：

| 修饰 | 效果 | 代价 |
|---|---|---|
| 大宗采购 | 需求数量提高，金钱收益提高 | 增加不稳定度 |
| 优质客户 | 最低质量提高，收益评分奖励提高 | 增加不稳定度 |
| 回头客 | 声望收益提高 | 金钱收益略降 |
| 快速结算 | 回礼包数量提高 | 交付窗口变短 |
| 菜单明确 | 条目随机范围缩小 | 起拍价或制作成本提高 |

负面修饰：

| 修饰 | 效果 |
|---|---|
| 挑剔 | 最低质量提高，但没有额外收益 |
| 预算紧张 | 金钱收益降低 |
| 临时改菜单 | 额外增加一个需求条目 |
| 采购混乱 | 同一类需求可能重复出现 |
| 急单 | 必须在较短时间内交付 |

规则建议：

- 每添加一个正面催化剂，增加 `Instability`。
- 当 `Instability` 超过阈值时，应用催化剂有概率附带负面修饰。
- 同类强修饰不能无限叠加，例如不能连续堆多个 `大宗采购`。
- 催化剂对当前草稿的结果应可预览，但不是所有细节都要完全显示。

## 订单构筑台

第一版已经使用 MBD2 `createdelight:order_builder` 实现为“订单构筑台”。

当前基础交互：

- 手持订单印章右键构筑台，会尝试把方向写入另一只手中的订单草稿。
- 手持订单草稿右键构筑台，另一只手有印章时会写入印章；否则直接开封生成正式订单。
- 逻辑由 `kubejs/server_scripts/mbd2/order_builder.js` 事件脚本驱动，不使用配方，因为这里需要读取和写入 NBT。
- 普通右键订单草稿和印章的旧流程仍保留，避免破坏已有使用习惯。

后续 UI 交互：

- 左槽：订单草稿。
- 右侧槽：印章、催化剂、重签章等材料。
- 中间显示当前草稿预览。
- 点击确认后，把修饰写入草稿 NBT。
- 草稿仍然需要右键开封，或者在构筑台内直接开封。

预览信息建议：

- 顾客倾向：例如“人类较高”“精灵较高”。
- 菜单倾向：例如“饮品”“甜品”“宴席”。
- 印章解释：显示当前印章具体影响哪些顾客或品类，而不是只显示印章名称。例如“主食”应列出主食、面包、米饭、面条、饺子、三明治、卷饼等可能需求，并标出哪些权重更高。
- 规模：小单、普通、大宗。
- 质量要求：普通、较高、苛刻。
- 收益倾向：金币、声望、回礼。
- 不稳定度：低、中、高、危险。

不要一开始就做过度复杂的 UI。第一版可以只显示文本和图标，后续再做更精细的列表。

订单解析器可以承担更完整的预览职责。构筑台负责把印章写进草稿，解析器负责解释草稿或印章：某个顾客印章会提高哪些顾客池，某个菜单印章会提高哪些订单品类，以及这些方向在当前玩家声望下大概可能生成哪些订单。这样玩家不用去查数据文件，也能理解“饮品”“主食”“宴席”等词到底对应什么。

## 生成接口改造

当前接口：

```js
Order.create(player)
```

建议扩展为：

```js
Order.create(player, spec)
```

`spec` 示例：

```js
{
  seed: 123456789,
  customerTags: ["human"],
  categoryTags: ["drink"],
  customerWeightBonus: {
    human: 3.0
  },
  categoryWeightBonus: {
    tea: 2.0,
    coffee: 1.5,
    juice: 1.5
  },
  minRarity: "COMMON",
  maxRarity: "RARE",
  countMultiplier: 1.5,
  moneyMultiplier: 1.25,
  reputationMultiplier: 1.0,
  minQualityBonus: 1,
  extraEntryChance: 0.2,
  deadlineTicks: 24000
}
```

实现原则：

- 没有 `spec` 时保持当前行为。
- 印章先改变顾客池和条目池权重。
- 催化剂再修改数量、质量、收益和特殊限制。
- 最终订单仍写入 `createdelightOrderInfo`，交付器读取方式尽量不变。

订单 NBT 可增加：

```js
{
  createdelightOrderInfo: {
    type: "human_tea_house",
    entries: [...],
    ownerName: "...",
    ownerUUID: "...",
    generatedReputationLevel: 3,
    modifiers: ["bulk_order", "quality_request"],
    deadlineGameTime: 1234567,
    rewardMultipliers: {
      money: 1.25,
      reputation: 1.0,
      gift: 1.1
    }
  }
}
```

交付器只需要在结算时额外读取 `rewardMultipliers` 和 `deadlineGameTime`。没有这些字段时按旧订单处理。

## 获取渠道

拍卖行不应只卖未开封订单，而应逐步卖订单构筑材料。

建议渠道：

| 渠道 | 出售内容 | 定位 |
|---|---|---|
| 拍卖行 | 随机草稿、稀有印章、稀有催化剂 | 机会型 |
| LC 商店 | 基础草稿、基础印章 | 稳定入口 |
| 订单回礼 | 催化剂、重签章、高级印章碎片 | 正反馈 |
| 任务书 | 初始草稿和基础印章 | 教学 |
| 常驻合同 | 可周期生成同类订单 | 后期自动化 |

## 常驻合同

常驻合同是后期自动化的关键。

效果：

- 放入机器后，按冷却生成同类型订单草稿或正式订单。
- 合同决定顾客或菜单方向，例如“人类茶馆供货合同”。
- 每次生成的数量和质量仍有波动。
- 奖励略低于高风险随机订单，但稳定可自动化。

限制：

- 每台机器只能激活一个合同。
- 同时激活合同数量受订单声望限制。
- 生成订单需要手续费或消耗空白订单。
- 高级合同需要完成对应顾客若干次后解锁。

这个设计能把订单系统从“一次性任务”推进到“长期供货线”。

## 平衡建议

### 可控性成本

订单越可控，基础收益应越低或成本越高。

建议：

- 完全随机订单：收益最高。
- 使用一个印章：收益轻微降低或成本提高。
- 使用两个印章：收益进一步降低，但更适合自动化。
- 常驻合同：收益最低但最稳定。
- 高不稳定催化订单：收益最高，但更难完成。

### 不稳定度

建议阈值：

| 不稳定度 | 显示 | 效果 |
|---:|---|---|
| 0-19 | 稳定 | 无额外风险 |
| 20-39 | 波动 | 小概率附带负面修饰 |
| 40-69 | 不稳定 | 中概率附带负面修饰 |
| 70-99 | 危险 | 高概率附带负面修饰 |
| 100+ | 失控 | 开封时可能强制增加负面修饰 |

不建议让草稿直接作废。失控也应产生订单，只是订单更难或收益结构更偏风险。

## 分阶段实现

### 当前分支目标

`feat/order-draft-seals` 当前已经落地以下基础能力：

1. 订单生成参数化。

   已将 `Order.create(player)` 扩展为 `Order.create(player, spec)`。`spec` 用来表达顾客倾向、菜单倾向、品类倾向、数量倍率、质量修饰和收益倍率。没有 `spec` 时保持旧逻辑，确保现有未开封订单、拍卖行订单和任务奖励不回归。

2. 订单草稿与基础印章。

   已复用 `createdelight:unopened_order` 作为订单草稿载体。基础印章使用同一个 `createdelight:order_seal` 物品，通过 `OrderSeal` NBT 区分方向，并把顾客或菜单倾向写入 `OrderDraft` NBT。玩家开封时读取这些倾向并生成对应订单。

3. 稳定入口与订单构筑台。

   LC 订单商会商店已经出售基础订单和 8 种基础印章；入门任务奖励已经包含未开封订单、饮品印章和甜品印章；MBD2 订单构筑台已经通过事件脚本支持草稿 + 印章。

4. 基础市场饱和。

   完成订单后记录玩家近期交付的顾客和品类；后续生成类似订单时，金币收益会轻微软降并随游戏日衰减。

这一阶段已经验证“玩家可以选择订单方向，但不能直接指定最终货物”。下一步应优先补构筑台 UI、催化剂/重签章和常驻合同，而不是继续堆更多基础印章。

### 第一阶段：可筛选开封

- 已完成：给 `Order.create(player, spec)` 加可选参数。
- 已完成：新增一个订单印章物品，并用 NBT 提供少量基础印章变体。
- 已完成：右键未开封订单时，如果 NBT 有印章信息，就按印章筛选生成。
- 已完成：拍卖行继续刷新普通未开封订单。

### 第二阶段：订单构筑台

- 已完成第一版：新增 MBD2 订单构筑台。
- 已完成：支持草稿 + 印章 -> 带 NBT 的草稿。
- 已完成：将基础印章加入 LC 商店和任务奖励。
- 待做：支持基础预览文本和更明确的 UI。

### 第三阶段：催化剂与不稳定度

- 新增正面/负面修饰。
- 增加 `Instability`。
- 订单结算读取收益倍率和限时字段。
- 拍卖行和回礼加入催化剂。

### 第四阶段：常驻合同

- 新增合同道具。
- 支持机器周期性生成订单。
- 合同和自动请求器配合，形成后期供货自动化。
- 根据声望限制合同数量或合同等级。

## 与现有自动化的关系

订单请求器负责把订单需求转换为 Create 包裹请求。订单构筑系统负责让玩家拿到更适合当前产线的订单。

两者分工：

- 构筑台：决定“接什么订单”。
- 请求器：决定“用仓库里的哪些物品交付”。
- 交付器：决定“是否完成、给多少奖励”。

这样不会把所有复杂度塞进请求器，也能让订单获取本身成为一个可成长的系统。

## 待确认问题

- 订单构筑台第一版已经采用 MBD2 机器和事件脚本；是否迁移到 CDC Java 方块取决于后续 UI 复杂度。
- 当前印章按消耗品处理；后续如果引入“许可证”式印章，应作为另一类高级道具，而不是替换基础印章。
- 催化剂是否允许多个同类叠加。
- 常驻合同生成的是未开封订单，还是直接生成正式订单。
- 限时订单是否需要真实过期，还是只影响收益倍率。
## 订单解析器落地状态

订单解析器已承担草稿/印章解释职责。玩家可以把 `createdelight:order_seal` 放进解析器查看该印章的具体含义：顾客印章会列出可能指向的顾客订单池，菜单印章会列出可能生成的订单品类与权重。玩家也可以把已经写入方向的 `createdelight:unopened_order` 放进去，同时查看顾客方向和菜单方向。

这使构筑台和解析器形成明确分工：构筑台负责写入方向和开封草稿，解析器负责解释方向会带来哪些可能结果。后续如果加入催化剂、重签章或合同碎片，也应优先让解析器显示这些修饰对订单生成池、数量、质量和收益的影响。
