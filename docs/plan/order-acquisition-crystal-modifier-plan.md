# 订单获取与订单修饰系统计划

本文记录一种参考 Vault Hunters 3 宝库水晶修饰思路的订单获取方案。核心目标不是复制宝库系统，而是把本包当前“拍卖行随机刷新未开封订单”的入口，改造成一个可被玩家逐步控制、可与自动化生产线配合的“订单构筑”系统。

## 设计目标

- 订单获取不能长期只依赖拍卖行随机盲盒。
- 玩家应能把订单导向自己已经建设的产线，例如茶、甜品、快餐、酒类或怪物餐。
- 可控性需要付出成本，不能让玩家无风险稳定刷最高收益订单。
- 订单自动化后，玩家应能获得稳定订单来源，而不是一直手动等拍卖行。
- 当前 `createdelight:unopened_order -> 右键生成 createdelight:order` 的流程应保留，并作为新系统的基础。

## 当前状态与问题

当前入口已经从单纯拍卖行盲盒推进到“随机订单 + 稳定购买 + 基础构筑”并存：

- 任务奖励给 `createdelight:unopened_order`，并额外给入门菜单印章。
- Lightman's Currency 拍卖行每半天刷新 1-3 个 `createdelight:unopened_order`。
- LC 订单商会商店出售未开封订单和基础印章。
- 玩家可以直接右键 `createdelight:unopened_order` 开封，也可以先用 `createdelight:order_seal` 写入方向。
- MBD2 `createdelight:order_builder` 已作为第一版订单构筑台，使用事件脚本处理草稿和印章。
- 完成订单后会记录玩家近期交付的顾客和品类，后续同方向订单会受到轻微软性的市场饱和金币折扣。

截至 2026-08-02，第一批订单分级和条款已经落地：

- 正式订单写入独立 `orderGrade`，普通货量按 I-VI 级目标区间生成，不再使用 `sqrt(声望等级)` 直接放大。
- 新增通用 NBT 物品 `createdelight:order_clause`，第一批实现 11 个扶持、生产、验收和结算条款。
- 构筑台两个预留槽已启用为条款槽；解析器和物品提示会显示等级、条款及金币/声望/回礼倍率。
- `reputationMultiplier` 和回礼倍率已经进入实际结算；订单商会开始出售中后期条款，入门任务限量给予 3 枚“新手上路”。

仍然存在的问题：

- 当前金币仍主要由货量和品类 `base_count` 决定，还没有独立的品类价值权重与订单等级基础费。
- 条款商店已有第一批货币出口，但尚未按声望做个人白名单分层供货。
- 订单来源仍然缺少后期常驻合同，不能完全承担持续自动化供货。
- 市场饱和当前只作为交付时的金币折扣，尚未接入更完整的公告板或合同市场。

## 核心概念

### 订单草稿

`createdelight:unopened_order` 改为“订单草稿”的基础载体。它仍然可以直接右键打开，但也可以先经过工作台修饰。

概念 NBT：

```js
{
  OrderDraft: {
    Seed: 123456789,
    Grade: 3,
    Seals: ["customer_human", "category_drink"],
    Catalysts: ["bulk", "premium"],
    Modifiers: ["bulk_order", "quality_request"],
    Instability: 15,
    Revision: 2
  }
}
```

当前实际落地的基础 NBT 更轻量：

```js
{
  OrderDraft: {
    Revision: 1,
    customerSeal: "human",
    categorySeal: "drink"
  }
}
```

当前使用 `customerSeal` 和 `categorySeal`，每个草稿最多保存一个顾客方向和一个菜单方向。后续催化剂、不稳定度、重签章和 seed 预览再扩展到概念 NBT。

说明：

- `Seed` 决定随机结果，方便同一草稿在预览和开封时保持一致。
- `Grade` 表示单张订单自身的难度等级，不直接等同于玩家声望等级。
- `Seals` 是玩家明确指定的订单方向。
- `Catalysts` 是输入过的修饰道具记录。
- `Modifiers` 是最终应用到订单生成上的效果。
- `Instability` 表示订单不稳定度，越高越容易出现负面修饰或失败。
- `Revision` 便于后续版本兼容旧 NBT。

### 订单印章

订单印章用于决定订单大方向，相当于“这个订单属于谁、偏向什么菜单”。

实现上不需要为每一种印章注册独立物品。第一版使用一个 `createdelight:order_seal`，通过 `OrderSeal` NBT 区分人类、精灵、饮品、甜品等方向；具体方向配置放在 `kubejs/startup_scripts/custom/order/data.js`。

第一批建议：

| 印章 | 作用 | 解锁建议 |
|---|---|---|
| 人类商会印章 | 提高人类顾客权重 | 声望 1 |
| 精灵茶会印章 | 提高精灵顾客权重 | 声望 2 |
| 矮人酒馆印章 | 提高矮人顾客权重 | 声望 2 |
| 怪物餐馆印章 | 提高怪物顾客权重 | 声望 3 |
| 饮品菜单印章 | 提高茶、果汁、酒、咖啡权重 | 声望 2 |
| 甜品菜单印章 | 提高蛋糕、派、冰淇淋、果冻权重 | 声望 2 |
| 主食菜单印章 | 提高面包、米饭、面条、饺子权重 | 声望 3 |
| 宴席菜单印章 | 提高多条目、高数量订单权重 | 声望 4 |

规则建议：

- 一个草稿最多有 1 个顾客印章和 1 个菜单印章。
- 低级印章只改变权重，不完全锁定结果。
- 高级印章可以更接近锁定，但需要更高声望或更高费用。

### 声望等级与订单等级

玩家声望和单张订单难度应拆成两个维度：

- 声望等级决定顾客、订单等级、催化剂和合同的可用范围。
- 订单等级决定单张订单的基础条目数、货量、品质和奖励。
- 顾客稀有度只描述顾客池，不再同时承担玩家阶段和订单难度两种职责。

建议保留当前声望阈值 `0 / 10 / 20 / 40 / 60 / 100`，增加独立的 `orderGrade`：

| 订单等级 | 名称 | 条目数 | 目标总需求量 | 品质方向 | 典型内容 |
|---:|---|---:|---:|---|---|
| I | 试单 | 1 | 32-96，中位约 64 | 普通 | 面包、作物、基础饮品 |
| II | 常规订单 | 1-2 | 64-160，中位约 112 | 普通为主 | 简单加工食品 |
| III | 商会订单 | 2-3 | 128-320，中位约 224 | 普通/优良 | 组合菜单、稳定量产 |
| IV | 专业订单 | 2-4 | 192-512，中位约 352 | 优良，偶尔精品 | 酒类、宴席、复杂料理 |
| V | 大客户订单 | 3-4 | 320-768，中位约 544 | 优良/精品 | 大宗、高品质、多产线协作 |
| VI | 盛典订单 | 3-5 | 512-1024，中位约 768 | 精品为主 | 节庆、跨族宴会、特殊回礼 |

大宗订单不应成为所有高声望订单的默认形态。`大宗采购` 等规模修饰可以把 V-VI 级订单继续推到 1000-2500 件，而普通订单保留更适合日常周转的体量。

声望等级推荐抽取范围：

| 声望等级 | 身份 | 常见订单等级 |
|---:|---|---|
| 1 | 见习供货商 | I |
| 2 | 登记供货商 | I-II |
| 3 | 认证供货商 | II-III |
| 4 | 商会伙伴 | II-IV |
| 5 | 核心供货商 | III-V |
| 6 | 首席承包商 | IV-VI |

同一声望等级内仍应保留简单订单。高级玩家可以选择接小单周转、普通订单稳定经营，或者用催化剂和合同承接高阶订单。

### 订单催化剂与修饰

订单催化剂用于改变订单的生产形态、验收条件或结算偏向。方向印章不占修饰槽；顾客印章、菜单印章和订单修饰属于三个不同层次。

#### 新手与扶持修饰

| 修饰 | 效果 | 获取与限制 |
|---|---|---|
| 新手上路 | 货物要求降至 25%，最终金币约为原订单的 50%，声望约为 50% | 任务和初期里程碑总共给予约 3 枚，只能用于 I-II 级订单，声望 3 后不再获取 |
| 小单试做 | 最多一个条目，货量约为 70%，最终收益约为 65% | 入门任务少量给予 |
| 宽松验收 | 最低品质降低一级，金币约为 75%，声望约为 80% | 声望 1-3 可用 |
| 商会保荐 | 订单等级降低一级，声望仍保留原订单约 80% | 首次达到声望 2 时少量给予 |
| 试营业补贴 | 金币略高，但不产生主题回礼 | 仅作为前几张订单的扶持材料 |

当前金币公式已经随实际交付量同比缩放，因此 `新手上路` 若要实现“数量为 25%，最终收益仍为 50%”，对应生成规格应近似使用 `countMultiplier = 0.25` 和 `moneyMultiplier = 2.0`，而不是把 `moneyMultiplier` 设置为 `0.5`。

#### 生产方式修饰

| 修饰 | 效果 | 适合产线 |
|---|---|---|
| 专品专供 | 条目数减少，单项数量约为 160%，总收益小幅提高 | 少数大型专线 |
| 零担拼单 | 条目数增加，单项数量约为 55%，金币略增，声望提高 | 大型综合仓库 |
| 薄利多销 | 总数量约为 200%，单位收益降低，最终金币约为 150%，市场热度增加 | 高吞吐产线 |
| 小而精 | 数量约为 50%，最低品质 +1，金币和声望略增 | 品质农业和精品加工 |
| 整箱采购 | 数量向完整栈、整组或包裹单位取整，金币约提高 8% | Create 包裹物流 |
| 菜单从简 | 只保留一个核心品类，金币略降 | 单线起步玩家 |
| 宴席拼盘 | 增加条目、降低单项数量，并提高多样性收益 | 多模块厨房 |
| 不限菜单 | 放弃精确菜单方向，金币提高约 15% | 接受随机需求的仓库 |
| 回头客 | 固定顾客方向并降低数量波动，但市场热度增长更快 | 稳定主题产线 |
| 联名菜单 | 从两个菜单组混合抽取条目，金币和声望提高 | 中后期综合产线 |

#### 结算偏向修饰

| 修饰 | 金币 | 声望 | 回礼或额外效果 |
|---|---:|---:|---|
| 口碑优先 | 70% | 175% | 标准回礼 |
| 现款结算 | 135% | 50% | 回礼减少或取消 |
| 礼尚往来 | 70% | 100% | 回礼数量或稀有度提高 |
| 商会履历 | 85% | 135% | 更容易获得合同碎片 |
| 一锤子买卖 | 120% | 75% | 市场热度额外增加 |
| 长期合作 | 85% | 110% | 提高对应合同履约度 |

当前 `reputationMultiplier` 已能写入订单 NBT，但声望结算尚未实际应用，解析器也没有显示这一倍率。实现声望型修饰前必须先补齐这两个环节。

#### 高风险与稀有修饰

| 修饰 | 效果 | 出现阶段 |
|---|---|---|
| 大宗采购 | 数量约为 250%，金币系数约为 115%，声望提高，市场热度增加 | III+ |
| 品质抽检 | 最低品质 +1，金币约为 135%，声望提高 | III+ |
| 典藏级 | 数量减半，但要求精品品质，回礼稀有度提高 | V+ |
| 加急配送 | 两个游戏日内完成时金币 +35%，之后恢复普通收益 | III+ |
| 特急救场 | 一个游戏日内完成时金币 +75%，之后恢复普通收益 | V+ |
| 行情缺口 | 市场饱和惩罚减半，金币提高约 15% | 仅由系统生成 |
| 反季采购 | 抽取本阶段较少见的品类，金币提高约 35% | IV+ |
| 越级挑战 | 订单等级提高一级，金币 +25%，声望 +50% | II+，最多越一级 |
| 盛典承办 | 多条目、高品质并提供特殊主题回礼 | VI |
| 连锁开业 | 连续生成三张同方向订单，全部完成后追加奖励 | IV+ |

普通订单不设置硬性过期。加急和特急只让额外奖金失效，不让订单本身作废。

#### 修饰组合规则

- 规模、菜单、验收、结算、时效、市场各为一个修饰类别，同类最多一个。
- I-II 级订单最多 1 个修饰，III 级最多 2 个，IV-V 级最多 3 个，VI 级可以额外带一个系统生成的盛典条款。
- `新手上路` 不得与 `大宗采购`、`越级挑战`、加急或特急同时存在。
- 同类强修饰不允许叠加；收益按最终货量和最终条件计算，不直接把文案倍率相乘后展示。
- 构筑台显示方向和修饰，解析器显示最终预计条目、货量、品质、金币、声望和特殊条件。
- `Instability` 暂不作为第一批必需机制；先用类别互斥、订单等级和修饰槽控制组合强度，确认仍需要随机负面条款后再加入不稳定度。

## 订单构筑台

第一版已经使用 MBD2 `createdelight:order_builder` 实现为“订单构筑台”。

当前基础交互：

- 手持订单印章右键构筑台，会尝试把方向写入另一只手中的订单草稿。
- 手持订单草稿右键构筑台，另一只手有印章时会写入印章；否则直接开封生成正式订单。
- 逻辑由 `kubejs/server_scripts/mbd2/order_builder.js` 事件脚本驱动，不使用配方，因为这里需要读取和写入 NBT。
- 普通右键订单草稿和印章的旧流程仍保留，避免破坏已有使用习惯。

后续 UI 交互：

- 左槽：订单草稿。
- 右侧槽：印章、催化剂、重签章等材料。
- 中间显示当前草稿预览。
- 点击确认后，把修饰写入草稿 NBT。
- 草稿仍然需要右键开封，或者在构筑台内直接开封。

预览信息建议：

- 顾客倾向：例如“人类较高”“精灵较高”。
- 菜单倾向：例如“饮品”“甜品”“宴席”。
- 印章解释：显示当前印章具体影响哪些顾客或品类，而不是只显示印章名称。例如“主食”应列出主食、面包、米饭、面条、饺子、三明治、卷饼等可能需求，并标出哪些权重更高。
- 规模：小单、普通、大宗。
- 质量要求：普通、较高、苛刻。
- 收益倾向：金币、声望、回礼。
- 不稳定度：低、中、高、危险。

不要一开始就做过度复杂的 UI。第一版可以只显示文本和图标，后续再做更精细的列表。

订单解析器可以承担更完整的预览职责。构筑台负责把印章写进草稿，解析器负责解释草稿或印章：某个顾客印章会提高哪些顾客池，某个菜单印章会提高哪些订单品类，以及这些方向在当前玩家声望下大概可能生成哪些订单。这样玩家不用去查数据文件，也能理解“饮品”“主食”“宴席”等词到底对应什么。

## 生成接口改造

当前接口：

```js
Order.create(player)
```

建议扩展为：

```js
Order.create(player, spec)
```

`spec` 示例：

```js
{
  seed: 123456789,
  customerTags: ["human"],
  categoryTags: ["drink"],
  customerWeightBonus: {
    human: 3.0
  },
  categoryWeightBonus: {
    tea: 2.0,
    coffee: 1.5,
    juice: 1.5
  },
  minRarity: "COMMON",
  maxRarity: "RARE",
  countMultiplier: 1.5,
  moneyMultiplier: 1.25,
  reputationMultiplier: 1.0,
  minQualityBonus: 1,
  extraEntryChance: 0.2,
  deadlineTicks: 24000
}
```

实现原则：

- 没有 `spec` 时保持当前行为。
- 印章先改变顾客池和条目池权重。
- 催化剂再修改数量、质量、收益和特殊限制。
- 最终订单仍写入 `createdelightOrderInfo`，交付器读取方式尽量不变。

订单 NBT 可增加：

```js
{
  createdelightOrderInfo: {
    type: "human_tea_house",
    entries: [...],
    ownerName: "...",
    ownerUUID: "...",
    generatedReputationLevel: 3,
    modifiers: ["bulk_order", "quality_request"],
    deadlineGameTime: 1234567,
    rewardMultipliers: {
      money: 1.25,
      reputation: 1.0,
      gift: 1.1
    }
  }
}
```

交付器只需要在结算时额外读取 `rewardMultipliers` 和 `deadlineGameTime`。没有这些字段时按旧订单处理。

## 获取渠道

拍卖行不应只卖未开封订单，而应逐步卖订单构筑材料。

建议渠道：

| 渠道 | 出售内容 | 定位 |
|---|---|---|
| 拍卖行 | 随机草稿、稀有印章、稀有催化剂 | 机会型 |
| LC 商店 | 基础草稿、基础印章 | 稳定入口 |
| 订单回礼 | 催化剂、重签章、高级印章碎片 | 正反馈 |
| 任务书 | 初始草稿和基础印章 | 教学 |
| 常驻合同 | 可周期生成同类订单 | 后期自动化 |

## 常驻合同

常驻合同是后期自动化的关键，但它不是一张无限使用的订单，而是一个可重复生成订单的供货模板。

基础流程：

```text
供货合同放入合同调度台
  -> 消耗空白订单和手续费
  -> 生成带固定方向和合同条款的订单草稿
  -> 构筑台可追加一个允许的修饰
  -> 开封为正式订单
  -> 解析器、请求器、Create 包裹和提交口完成履约
```

每份合同同一时间只能存在一张未完成订单。上一张订单未完成或未主动撤销时，合同不会继续堆积订单；玩家离线或区块未加载不会造成合同失败。

### 合同等级

| 合同 | 解锁 | 行为 |
|---|---:|---|
| 试用合同 | 声望 4 | 固定一个顾客或菜单方向，持续约 5 个周期，生成 II-III 级订单 |
| 常驻合同 | 声望 5 | 固定顾客和菜单，可选择一个长期生产修饰，生成 III-IV 级订单 |
| 核心合同 | 声望 6 | 可配置两个条款并安装自动签发模块，生成 IV-V 级订单，偶尔出现 VI 级订单 |
| 盛典合同 | 特殊获取 | 有限周期生成 VI 级主题订单和特殊回礼 |

同时激活合同数量建议为声望 4 时 1 份、声望 5 时 2 份、声望 6 时 3 份。高级合同还应要求完成对应顾客或菜单方向的若干订单，避免只靠金币直接购买全部自动化能力。

### 合同收益和履约度

- 合同基础金币约为同等级随机订单的 85%，因为稳定性本身就是主要收益。
- 合同订单只承受约一半市场饱和惩罚，但也只产生约一半市场热度。
- 连续履约可以把基础收益逐步提高到约 95%，但不能超过高风险随机订单。
- 未完成订单只会阻塞下一周期，不销毁合同；主动撤销需要手续费或降低履约度。
- 合同可以携带一个固定生产修饰和一个系统轮换条款，使产线方向稳定但每张订单仍有少量变化。

### 自动签发

普通合同生成订单草稿，保留构筑玩法。声望 6 可以制作自动签发模块，保存玩家已经确认过的合同模板，自动把草稿开封成正式订单并交给请求器。最终自动化仍然生成真实订单、真实 Create 请求和真实包裹，不直接从仓库扣除物品结算。

这样合同前期不会绕过构筑台，后期又能成为中心仓库、请求器和提交口组成的完整自动化终点。

## 平衡建议

### 当前数量与奖励审计

按当前 `Order.create` 逻辑进行只读模拟：每个声望等级生成 200000 张无印章订单，按最低合格品质、评分 1、无市场饱和计算。结果如下：

| 声望等级 | 总需求量 10%分位 | 中位数 | 90%分位 | 基础金币中位数 |
|---:|---:|---:|---:|---:|
| 1 | 128 | 268 | 560 | 约 32.5 金币 |
| 2 | 104 | 308 | 668 | 约 82.5 金币 |
| 3 | 164 | 424 | 904 | 约 119 金币 |
| 4 | 228 | 520 | 1092 | 约 148 金币 |
| 5 | 288 | 600 | 1280 | 约 170 金币 |
| 6 | 336 | 668 | 1428 | 约 188 金币 |

这里的“金币”指 `createdelightcore:gold_coin` 等值；货币链为 10 铁币 = 1 铜币、10 铜币 = 1 金币。声望 2 的低分位偶尔低于声望 1，是因为新解锁顾客包含基础数量较小的品类，但整体中位数仍继续上升。

结论：

- 当前前期要求量明显偏大。声望 1 的典型订单已经需要约 268 件，最重的 10%达到 560 件，不符合“第一次试单”的教学定位。
- 阶段差被压缩。声望 1 中位数已经达到声望 6 中位数的约 40%，玩家很早就被要求建设中型量产线。
- 声望 4-6 的 500-1400 件在请求器和提交口自动化后并非不能接受，但不应反推前期也使用同一数量公式。
- 当前基础金币约为每件货物 20-28 铁币等值；普通食品直接售卖的基准通常约为每件 5 铁币，因此订单提供约 4-6 倍单位溢价，作为有品类、品质和批量限制的订单本身并不算低。
- 真正的问题不是金币数字太少，而是货币消费出口不足、订单草稿成本相对回报过低，以及回礼数量又随订单条目数和评分继续增长。

因此数量应先按订单等级降低和分层，金币则不要简单同比砍掉。前期应减少总投入并保留较高单位溢价；后期通过订单等级、大宗修饰和合同把货量重新抬高。

第一版分级逻辑落地后再次进行 100000 张/声望等级的静态模拟，得到：

| 声望等级 | 总需求量 10%分位 | 中位数 | 90%分位 | 基础金币中位数 |
|---:|---:|---:|---:|---:|
| 1 | 40 | 64 | 88 | 约 10.2 金币 |
| 2 | 48 | 84 | 144 | 约 16.7 金币 |
| 3 | 80 | 144 | 276 | 约 38.2 金币 |
| 4 | 112 | 228 | 404 | 约 59.4 金币 |
| 5 | 204 | 364 | 620 | 约 100.4 金币 |
| 6 | 332 | 564 | 852 | 约 171.1 金币 |

声望 1 的普通订单已经回到 32-96 件目标内；“新手上路”应用于 I 级订单时中位约 16 件、基础金币约 4.7 枚，符合“要求减少 75%，最终金币保留约一半”的目标。这里仍是最低合格品质、评分 1、无市场折扣的静态结果，实际游戏中的品类成本、品质评分与货币消费速度仍需回归。

### 推荐奖励锚点

在评分 1、无市场折扣、无高收益修饰时，建议把各订单等级的金币中位区间控制为：

| 订单等级 | 目标总需求量 | 建议基础金币区间 |
|---:|---:|---:|
| I | 32-96 | 6-12 金币 |
| II | 64-160 | 12-25 金币 |
| III | 128-320 | 25-50 金币 |
| IV | 192-512 | 50-90 金币 |
| V | 320-768 | 90-150 金币 |
| VI | 512-1024 | 150-250 金币 |

这些数值是经济锚点，不是最终锁定值。订单奖励公式建议从“货量直接决定全部金币”调整为：

```text
最终金币 = 订单等级基础费
         + 各品类等效工作量 × 品类价值权重 × 订单单位溢价
         × 修饰倍率 × 品质评分 × 市场倍率
```

品类价值权重应配置在订单数据中。作物、普通饮料、复杂宴席、寿司和怪物料理不能只因为 `base_count` 接近就获得相近单位价格；但也不建议按玩家实际选择的具体物品价格结算，否则玩家会总是选择标签中成本最低的候选物。

### 奖励结构

金币不应承担订单系统的全部吸引力：

- I-II 级主要给予金币、基础声望和少量教学型构筑材料。
- III 级开始稳定产出催化剂、重签章或商会凭证。
- IV 级开始产出合同碎片并解锁声望供货。
- V-VI 级的核心奖励应是高级合同、稀有构筑材料、主题回礼和供货权限，而不是只增加金币位数。
- 回礼次数不再简单等于 `评分 × 条目数`；建议按订单等级设置基础回礼次数，品质和多样性只增加额外回礼概率。

建议基础回礼次数为 I 级 0-1 次、II 级 1 次、III 级 1-2 次、IV 级 2 次、V 级 2-3 次、VI 级 3-4 次。

### 货币消费出口

在最终确定金币倍率前，需要先为订单收入提供持续消费出口：

- 空白订单、基础印章、催化剂和重签章。
- 合同购买、激活手续费、续约和主动撤单费用。
- 商会出售的缺口原料、物流便利品和阶段性供货，但价格应高于玩家自建产线的边际成本。
- 声望解锁的合同许可证、自动签发模块和高级订单机器升级。
- 稀有主题回礼重抽、市场行情刷新或盛典订单报名费。

货币出口建立前，不建议因为“金币没用”继续提高订单金币；也不建议先把金币大幅削弱。先降低前期货量、建立订单等级和消费出口，再通过真实游戏回归调整单位溢价。

### 可控性成本

订单越可控，基础收益应越低或成本越高。

建议：

- 完全随机订单：收益最高。
- 使用一个印章：收益轻微降低或成本提高。
- 使用两个印章：收益进一步降低，但更适合自动化。
- 常驻合同：收益最低但最稳定。
- 高不稳定催化订单：收益最高，但更难完成。

### 可选的不稳定度

建议阈值：

| 不稳定度 | 显示 | 效果 |
|---:|---|---|
| 0-19 | 稳定 | 无额外风险 |
| 20-39 | 波动 | 小概率附带负面修饰 |
| 40-69 | 不稳定 | 中概率附带负面修饰 |
| 70-99 | 危险 | 高概率附带负面修饰 |
| 100+ | 失控 | 开封时可能强制增加负面修饰 |

不建议让草稿直接作废。失控也应产生订单，只是订单更难或收益结构更偏风险。第一批修饰优先使用类别互斥和修饰槽控制组合，不稳定度在基础分级跑通后再决定是否启用。

## 与现有自动化的关系

订单请求器负责把订单需求转换为 Create 包裹请求。订单构筑系统负责让玩家拿到更适合当前产线的订单。

两者分工：

- 构筑台：决定“接什么订单”。
- 请求器：决定“用仓库里的哪些物品交付”。
- 交付器：决定“是否完成、给多少奖励”。

这样不会把所有复杂度塞进请求器，也能让订单获取本身成为一个可成长的系统。

## 待确认问题

- 订单构筑台第一版已经采用 MBD2 机器和事件脚本；是否迁移到 CDC Java 方块取决于后续 UI 复杂度。
- 当前印章按消耗品处理；后续如果引入“许可证”式印章，应作为另一类高级道具，而不是替换基础印章。
- 基础催化剂同类不叠加；后续若引入许可证或合同升级，再单独定义可重复强化的上限。
- 普通常驻合同生成未开封订单草稿；声望 6 的自动签发模块可以按已确认模板直接生成正式订单。
- 普通订单永久有效；限时订单只影响额外收益，不影响订单可完成性。
- 各品类 `rewardWeight`、订单等级金币锚点和合同手续费仍需结合新增货币出口进行实机平衡。
## 订单解析器落地状态

订单解析器已承担草稿/印章解释职责。玩家可以把 `createdelight:order_seal` 放进解析器查看该印章的具体含义：顾客印章会列出可能指向的顾客订单池，菜单印章会列出可能生成的订单品类与权重。玩家也可以把已经写入方向的 `createdelight:unopened_order` 放进去，同时查看顾客方向和菜单方向。

这使构筑台和解析器形成明确分工：构筑台负责写入方向和开封草稿，解析器负责解释方向会带来哪些可能结果。后续如果加入催化剂、重签章或合同碎片，也应优先让解析器显示这些修饰对订单生成池、数量、质量和收益的影响。
