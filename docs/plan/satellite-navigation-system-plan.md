# 卫星导航与火箭坐标航行系统规划

本文规划一个与 Create: Northstar 火箭、星图和整合包冒险流程结合的“卫星系统”。玩家能够发射卫星、建立星球测绘能力、选择或扫描坐标，并把经过安全校验的坐标写入星图，使火箭可以直接前往该地点。

本系统的核心不是单纯提供传送，而是把“发现地点、建立轨道基础设施、规划着陆点、乘火箭抵达”做成一条可持续扩展的科技路线。

## 设计目标

- 玩家需要先制造并发射卫星，才能使用远程坐标导航。
- 卫星可以服务手动坐标、结构搜索、异常信号和后续资源扫描。
- 扫描结果最终写成 Northstar 星图的坐标目的地，由原生火箭系统执行航行。
- 服务端必须在写入星图前计算安全着陆点，不能把结构原始坐标直接交给火箭。
- 系统应支持单人、队伍共享、服务器权限和后续多种卫星模块。
- 核心功能不能依赖卫星实体永久加载区块或持续模拟轨道。

## 非目标

- 第一版不模拟真实轨道力学、轨道倾角、变轨和卫星碰撞。
- 第一版不让卫星成为持续加载区块的远程区块加载器。
- 第一版不允许客户端任意提交维度 ID 或未经服务端验证的着陆坐标。
- 卫星导航不替代星图科研、星球解锁、火箭燃料和自动着陆器。

## 推荐表现：混合卫星

卫星可以有三种实现路线：

| 路线 | 实现方式 | 优点 | 问题 |
|---|---|---|---|
| 纯虚拟 | 发射后只在服务器保存一条卫星记录 | 最稳定、低负载、适合多人服务器 | 视觉反馈较弱 |
| 完全实体 | 卫星作为实体、动态结构或轨道方块长期存在 | 直观，可接近、维修或破坏 | 需要区块加载、实体持久化、跨维度同步和轨道模拟 |
| 混合实现 | 功能状态是虚拟记录，实体或轨道结构只负责表现 | 可靠，且可以逐步增加视觉内容 | 需要明确表现层不参与权威判定 |

推荐采用混合实现：

- 卫星是否存在、归属、覆盖星球、模块、能量和扫描冷却由服务器 `SavedData` 或 CDC 能力保存。
- 发射成功后可以生成一次卫星升空动画、部署粒子或可选轨道模型。
- 若后续实现真实轨道卫星，实体丢失、区块卸载或模型异常不能删除服务器侧卫星能力。
- 玩家可以在轨道站看到卫星模型，也可以只在地面终端看到遥测状态。

这样第一版可以先完成玩法闭环，后续再判断真实卫星是否值得投入 Java 模组开发成本。

## 玩家流程

1. 玩家完成月球或地球轨道阶段，解锁卫星科技任务。
2. 制作“折叠测绘卫星”或“卫星载荷舱”。
3. 将载荷装入火箭或卫星发射设施。
4. 选择目标天体和轨道任务，消耗火箭燃料并发射。
5. 发射成功后，目标天体获得一颗可用卫星。
6. 玩家在“卫星导航终端”选择目标维度和导航模式。
7. 服务器取得目标 X/Z，并搜索安全着陆位置。
8. 玩家确认着陆点名称、风险和消耗。
9. 系统将 `Dimension`、`Position`、`Direction` 和标签写入星图。
10. 玩家把星图放入火箭核心，选择新坐标并正常起飞。

卫星只负责发现和登记目的地；火箭本身仍负责燃料、跨星球航行、自动着陆和返程。

## 发射方式

### 第一阶段：载荷部署原型

第一版优先验证功能，不立即修改 Northstar 火箭任务系统：

- 注册“折叠测绘卫星”物品或方块。
- 玩家乘火箭抵达目标轨道后部署载荷。
- 部署成功后消耗载荷，在队伍卫星列表中登记目标天体。
- 地球可在 `northstar:earth_orbit` 部署；没有轨道维度的星球暂时通过任务或专用发射终端登记。

这种方式开发成本最低，但“玩家亲自携带卫星上天”更像部署任务，而不是无人卫星发射。

### 第二阶段：正式卫星发射任务

正式版本由 CDC 扩展 Northstar 火箭：

- 新增卫星载荷方块、载荷舱或火箭站任务槽。
- 火箭控制界面增加“部署卫星”任务类型。
- 到达目标天体或轨道高度后消耗载荷，并注册服务器卫星记录。
- 火箭可以返航，也可以把卫星任务设计为一次性无人发射。
- 发射失败、火箭坠毁或任务取消时不得提前登记卫星。

这一阶段需要调查 `RocketContraption`、`RocketContraptionEntity`、`RocketStationBlockEntity` 和目标选择网络包的可扩展点。

### 第三阶段：视觉卫星

可选表现方案按成本从低到高排列：

1. 发射成功时播放部署音效、标题和轨道粒子。
2. 在轨道站终端显示旋转的卫星物品模型。
3. 在目标轨道维度的固定远处生成小型卫星结构。
4. 注册不参与逻辑判定的卫星实体或 Create 动态结构模型。

不建议第一版让真实卫星实体承担扫描、能量或所有权状态。

## 卫星与覆盖范围

卫星应绑定“天体或可导航维度组”，而不是全服务器通用。

示例：

| 卫星部署位置 | 建议覆盖范围 |
|---|---|
| 地球轨道 | 主世界、地球轨道中的坐标目标 |
| 月球轨道能力 | 月球、月背和月球附近轨道设施 |
| 火星轨道能力 | 火星地表与火星轨道 |
| 金星轨道能力 | 金星地表与金星轨道 |
| 深空中继卫星 | 已解锁星体之间的远程数据共享，不直接提供着陆点 |

若目标星球没有实际轨道维度，卫星记录仍可使用抽象的 `planet` 或覆盖组，不必为了卫星强行新增空维度。

## 卫星模块

卫星本体提供通信和坐标登记，功能由模块决定：

| 模块 | 功能 | 建议阶段 |
|---|---|---|
| 导航中继模块 | 玩家输入 X/Z，生成安全着陆点 | 基础卫星 |
| 地表测绘模块 | 在地图界面点选区域，显示高度和着陆风险 | 月球后 |
| 结构扫描模块 | 搜索允许列表中的结构 | 中期 |
| 生物群系扫描模块 | 搜索目标群系并返回附近安全地表点 | 中期 |
| 异常信号模块 | 发现任务结构、月背异常和特殊事件 | 剧情模块 |
| 高精度着陆模块 | 扩大平坦区域搜索范围，支持大型火箭 | 后期 |
| 深空通信模块 | 允许不同天体卫星共享扫描结果 | 后期 |

结构扫描不应默认支持所有注册结构。使用数据表维护白名单、阶段、扫描半径、消耗和是否允许重复发现。

## 卫星导航终端

终端界面建议分成四部分：

### 卫星列表

- 卫星名称和编号。
- 所属玩家或队伍。
- 覆盖天体。
- 当前模块。
- 能量、耐久或数据缓存。
- 扫描冷却状态。

### 目标选择

- 手动输入 X/Z。
- 从已有地图或星图点选。
- 选择结构或群系扫描。
- 选择任务提供的异常信号。
- 选择已有坐标进行重命名、共享或删除。

### 着陆预览

- 目标维度。
- 请求坐标与实际着陆坐标。
- 地表高度。
- 与结构中心的水平距离。
- 地形平整度、液体、障碍和净空风险。
- 是否需要自动着陆器或临时着陆平台。

### 确认写入

- 目的地名称。
- 写入的星图。
- 本次能量、数据或材料消耗。
- 风险警告。
- 确认后才修改星图 NBT。

第一版没有自定义 GUI 时，可以用方块菜单、聊天组件、任务界面或分步物品交互完成原型；正式版建议由 CDC 提供终端菜单和网络包。

## 坐标来源

### 手动坐标

玩家输入 X/Z，Y 可以省略。服务器根据目标维度类型计算最终 Y。

适合：

- 返回已知基地附近。
- 抵达队友提供的远方坐标。
- 探索远距离未生成区域。

### 地图点选

终端显示简化网格或与地图模组集成，点击后转换为 X/Z。客户端只提交选择结果，服务器仍需要重新验证边界和着陆安全。

### 结构扫描

服务器根据结构 ID、允许半径和阶段执行搜索。扫描结果先得到结构参考点，再在附近寻找安全地表位置。

地下结构的结果必须标注为“地表入口”，不能尝试让火箭降落到结构内部。

### 生物群系扫描

搜索目标群系后，以群系采样点为中心寻找着陆区。对于洞穴群系，同样只提供其上方或附近的安全地表点。

### 异常信号

任务、结构战利品或特殊遥测记录可以直接提供候选 X/Z，卫星负责校验、生成目标区块和建立坐标目的地。

## 安全着陆坐标计算

坐标导航必须经过统一的服务端着陆校验管线。

### 普通地表维度

1. 取得请求的 X/Z。
2. 检查世界边界、维度白名单和队伍权限。
3. 在目标点周围按螺旋或同心环搜索候选位置。
4. 使用 `Heightmap.Types.MOTION_BLOCKING_NO_LEAVES` 或验证后的 Northstar 等价高度取得地表 Y。
5. 按当前火箭碰撞箱检查整块着陆区域，而不是只检查中心方块。
6. 限制地面高差，基础卫星建议最大高差 1-2 格。
7. 排除岩浆、深水、粉雪、仙人掌、不可破坏方块和受保护领地。
8. 检查火箭高度加安全余量范围内的净空。
9. 选择评分最高的候选点并写入星图。

Northstar 在普通星球着陆时会根据地形重新计算着陆高度，但卫星仍应提前验证 X/Z 周围是否适合整艘火箭落地。

### 地下结构和洞穴群系

- 结构返回的 Y 只用于描述结构位置，不作为火箭目标。
- 在结构中心附近寻找地表点。
- 星图标签显示“远古城市地表入口”“异寂空谷地表入口”等名称。
- 可额外生成指南针、坐标记录或洞穴入口标记，帮助玩家从地表继续寻找。

### 轨道、虚空和空中目标

轨道维度不能依赖高度图：

- 必须提供精确 X/Y/Z。
- 目标必须存在经过验证的着陆平台、空间站甲板或导航信标。
- 写入前检查平台面积、火箭净空和方块碰撞。
- 若平台不存在，拒绝写入或消耗材料自动建造标准着陆平台。

Northstar 对轨道坐标会直接使用星图中的 Y 作为着陆高度。错误 Y 可能让自动着陆器制动过晚、发生碰撞，并因着陆速度超过安全值导致火箭爆炸。

### 大型火箭

安全半径不能固定为单个方块。正式实现应从当前火箭动态结构取得：

- 水平碰撞范围。
- 火箭总高度。
- 控制器或锚点相对位置。
- 自动着陆器是否存在。

如果终端无法读取具体火箭，使用保守的标准着陆区，并提示超大型火箭需要高精度着陆模块或人工平台。

## Northstar 星图集成

Northstar 坐标目的地使用 `RocketDestination`，星图中需要写入：

```text
Dimension: 目标维度 ID
Position: {X, Y, Z}
Direction: up
label: 目的地名称组件
```

已确认的机制边界：

- 火箭实际读取星图中的维度、坐标和方向。
- 对于同时包含坐标和方向的目的地，Northstar 0.6.1 发射时会在精确坐标查询 `ROCKET_WAYPOINT` POI；脚本除写入星图外，还必须在同一位置放置并保留 `northstar:rocket_waypoint`。
- 航点被破坏、坐标偏移一格或区块未正确登记 POI 时，火箭站会提示“缺少火箭航点”。
- 普通星球会计算地形着陆高度；轨道目的地使用记录的精确 Y。
- 卫星终端不能绕过星球科研、星球解锁或跨星际导航要求。

相关 Northstar 机制背景见 [冒险流程与配方魔改规划](./adventure-progression-overhaul-plan.md#northstar-机制附录)。

## 数据模型

推荐使用世界级 `SavedData`，并以队伍为默认所有权单位。

卫星记录至少包含：

```text
satelliteId
displayName
ownerType: player | team
ownerId
planetId 或 coverageGroup
deploymentDimension
deploymentTime
tier
modules[]
energy
durability
scanCooldowns{}
state: launching | active | damaged | offline
```

导航记录建议独立保存：

```text
navigationId
satelliteId
targetDimension
requestedPosition
landingPosition
direction
label
sourceType: manual | structure | biome | anomaly
sourceId
createdBy
createdTime
safetyScore
```

星图只保存 Northstar 能识别的目的地字段；所有权、扫描来源和安全评分保存在服务器数据中，避免依赖自定义 NBT 被 Northstar 原生界面保留。

## 能量与平衡

卫星不必逐 tick 模拟太阳能。推荐使用离散能量或扫描次数：

- 发射时获得基础能源。
- 每次坐标解析消耗少量能源。
- 结构、群系和异常扫描消耗更多能源并进入冷却。
- 可通过地面站上传电池、维护组件或数据介质进行补给。
- 后期卫星使用太阳能模块缓慢按世界时间结算能源，不要求区块加载。

建议限制：

- 基础卫星只能手动输入坐标。
- 结构扫描有半径、白名单和冷却。
- 高价值结构需要任务阶段或专用扫描数据。
- 同一目标附近重复扫描降低消耗，但不能无限复制战利品结构。
- 星图坐标数量仍受 Northstar 最大航点配置约束。

## 多人和权限

- 默认将卫星归属于 FTB Teams 队伍，而不是单个玩家。
- 队伍成员可以查看和使用坐标，只有队长或授权成员可以删除卫星、改名和公开坐标。
- 可将某个导航点复制到个人星图，但不能直接修改其他玩家背包。
- 公共服务器可设置公共卫星或公共导航终端。
- 客户端请求只提交操作类型和选择参数，维度、结构、权限和最终坐标全部由服务端判断。
- 对 FTB Chunks 领地执行着陆检查，避免火箭被引导进无权限领地。

## 性能约束

- 虚拟卫星不保持区块加载，也不逐 tick 扫描世界。
- 手动坐标只在玩家确认时加载或采样少量候选区块。
- 结构定位可能产生明显服务端开销，应限制半径、并发、冷却和可扫描结构。
- 大范围扫描建议进入服务器任务队列，每 tick 处理有限步骤，并在终端显示“扫描中”。
- 不因地图预览批量生成区块；只有确认着陆点时才允许生成目标附近必要区块。
- 真实卫星模型使用无 AI、无碰撞或纯客户端表现，避免成为常驻运算实体。

## 失败反馈

终端必须给出明确失败原因：

- 当前天体没有可用卫星。
- 卫星缺少对应扫描模块。
- 星球或维度尚未解锁。
- 目标超过世界边界。
- 未找到足够平坦的着陆区。
- 目标位于液体、危险方块或受保护领地。
- 轨道目标缺少有效着陆平台。
- 星图航点已满。
- 卫星能量不足或仍在冷却。
- 结构不在允许扫描列表或当前阶段不可见。

失败时不得写入半成品坐标，也不得消耗完整扫描成本；可以只消耗少量探测能源。

## 任务与流程定位

建议把卫星系统放在首次月球登陆之后：

1. 月球阶段教授星图和普通星球航行。
2. 月背异常任务教授遥测扫描和坐标目的地。
3. 完成月背或破损空间站后解锁基础卫星。
4. 火星阶段解锁结构扫描模块。
5. 金星或更后期解锁深空通信和高精度着陆模块。

这样卫星是对星图和火箭的扩展，而不是玩家第一次接触航天时就出现的复杂系统。

## 分阶段实施

### 阶段 A：技术验证

- 用 KubeJS 或调试物品向背包星图写入手动坐标。
- 验证普通星球与轨道维度的着陆差异。
- 验证不同大小火箭对平台面积和净空的要求。
- 验证未放置 `rocket_waypoint` 时坐标目的地仍可正常使用。

### 阶段 B：KubeJS 原型

- 注册折叠卫星、导航数据卡和临时终端。
- 使用玩家或队伍 persistent data 保存一颗基础卫星。
- 支持手动 X/Z、地表高度解析和星图写入。
- 对轨道维度只允许登记预设空间站坐标。
- 通过任务模拟卫星部署，不修改 Northstar 火箭源码。

### 阶段 C：CDC 正式系统

- 使用 `SavedData` 保存卫星和导航记录。
- 实现卫星导航终端 GUI、网络包、权限和队伍共享。
- 从火箭动态结构读取着陆占地。
- 实现结构、群系和异常扫描模块。
- 接入 FTB Chunks 领地与服务端扫描队列。

### 阶段 D：发射与表现

- 扩展 Northstar 火箭任务，支持卫星载荷部署。
- 增加发射、入轨和部署反馈。
- 根据实际开发成本决定是否增加轨道卫星结构或实体模型。

## 验证清单

- 普通星球手动坐标能生成安全地表目的地。
- 地下结构只生成地表入口，不会把火箭送入地下。
- 轨道坐标没有平台时会被拒绝。
- 轨道平台 Y 正确时自动着陆器不会因错误制动发生碰撞。
- 大型火箭不会因为只检查中心方块而卡入地形。
- 星图目的地写入后能被火箭站选择和通过服务端校验。
- 删除实体表现不会删除服务器卫星能力。
- 队伍成员可共享卫星，非成员不能修改。
- 世界重启、玩家离线和队伍变化后数据仍然正确。
- 扫描失败、取消或超时不会生成半成品航点。
- 结构扫描不会造成不可接受的主线程卡顿或大范围区块生成。

## 尚待决定

- 卫星是玩家随火箭部署，还是支持真正的无人发射任务。
- 第一版是否需要自定义 GUI，还是先用数据卡和聊天交互验证。
- 卫星能源采用离散扫描次数、FE 电池还是纯冷却。
- 月球等没有现成轨道维度的天体如何表现卫星部署。
- 是否允许卫星自动建造标准着陆平台，以及相应材料成本。
- 结构扫描白名单、扫描半径和阶段门槛。
- 火箭碰撞范围能否从 Northstar 运行时稳定取得，还是先采用固定安全规格。
- 真实卫星模型是否值得实现，以及采用结构、实体还是 Create 动态结构。

## 当前推荐结论

第一版采用“虚拟能力 + 可选视觉表现”的混合卫星，先实现卫星发射记录、手动坐标导航、安全着陆计算和星图写入。结构扫描与真实卫星模型放到后续阶段。

最重要的实现边界是：卫星负责找到目标附近的安全着陆点，而不是把原始结构坐标或任意 Y 直接交给火箭。普通星球可以根据高度图解析地表，轨道和虚空目标必须依赖精确坐标与已验证平台。
