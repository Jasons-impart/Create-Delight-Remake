# 通用酒瓶流体能力与森罗酒桶自动化计划

> 状态：调查完成，待实施；本轮只修订计划，不修改代码、配方、运行 JAR 或子模块指针。
> 日期：2026-11-21。
> 关联：[酿造分工与森罗酒馆适配](kaleidoscope-tavern-alcohol-integration-plan.md)。本文统一定义物品能力、KJS 配置和酒桶出料三部分的待实施方案。

## 目标与已确认事实

为缺少物品流体能力的固定瓶装酒增加标准 `IFluidHandlerItem`：CDC 实现满瓶内容、排液、返瓶和品质，KJS 提供内容数据。森罗酒桶统一读取能力，并保留 emptying、filling 后备，酿造完成后以真实流体保存产物，管道和水龙头共用一份库存。

已确认的实现约束：

- 森罗酒馆 `1.2.0` 本身将成品保存为物品份数并清空输入流体；CDC 当前延迟到初酿完成后才生成可取成品。
- Create Gears and Tavern（CGT）`1.2.0` 通过自己的饮品目录，把森罗成品转换为虚拟流体。外部酒不在目录中，所以仅给酒瓶补能力并不能自动修复现有酒桶，还需调整酒桶读取入口。
- 当前六款外部成品的类继承和相关能力提供器中，没有找到覆盖它们的物品流体能力。装排液配方不会自动附加这个能力。
- 当前 PowerfulJS `1.6.1` 提供 `CapabilityEvents.dynamicItem` 与 `CapabilityBuilder.FLUID.customItemStack()`。但它的 handler 继承 Forge `FluidHandlerItemStack`，默认读取 `Fluid` NBT；只设置容量不会预装酒液，默认排空仍是原物品，`onDrain` 也没有返回另一个空容器的接口。
- 本方案用 CDC 完整实现固定饮品容器，不在 KJS 中补持久化状态或 Java 反射逻辑；保留现有 PowerfulJS 能量能力脚本。

这些结论来自脚本、源码及本地 JAR 字节码核对，尚未完成本轮游戏实测。下文的新类和 API 均为拟新增接口，不代表已经存在。

## 一、CDC 提供通用物品流体能力

### 固定满瓶模型

首版支持“一个固定成品物品＝指定流体的固定液量”，例如一瓶苹果酒对应 250mB 苹果酒液，排空返回玻璃瓶。无需改动原物品类、饮用动作、食物属性、药效或原生喝完返瓶行为。

- 为每个目标 ItemStack 附加独立 provider，并缓存该栈自己的 handler；不同物品栈不共享可变状态，重复查询不会重新得到一瓶满酒。
- 内容由登记规则与当前单件物品确定，不依赖每个旧酒瓶预先写有 `Fluid` NBT。读取、能力查询和模拟不修改物品 NBT，也不将空的 NBT 储罐当作满瓶。
- `getFluidInTank(0)` 返回该单件酒瓶的准确流体、单份 mB 和品质副本；无效槽返回空。容量不固定为 250mB 或 1000mB。
- 支持两种 `drain` 重载，校验流体身份/NBT、请求量和当前容器状态。固定酒瓶采用整瓶排液：请求小于单份液量时返回空，请求足够时一次排出一份。
- `SIMULATE` 不消费；`EXECUTE` 后该 handler 不再提供酒液，`getContainer()` 返回一件正确的空容器。调用方依标准能力约定用返回容器替换已处理的酒瓶，不能只取得液体而保留原瓶。
- 默认只排液，`fill` 返回零；不把通用玻璃瓶注册成某一种固定酒，也不引入“排空后仍能喝的原酒瓶”。重新装瓶继续使用既有 Create filling 配方。
- 处理堆叠时先由调用方分出单件；handler 不直接将整组酒瓶作为一件容器排空。不能把单瓶液量乘以堆叠数后返回一只空瓶。

这与酒桶的连续排液不同：瓶装物品按完整一份转换，酒桶成品罐支持任意 mB，二者无需共用一种零头存储逻辑。

### 品质、既有能力与适用范围

- 流体品质由 `QualityUtils.getQuality(stack)` 与 QFF `withQuality` 等直接 API 桥接，不在能力的 `getFluid/getFluidInTank` 内调用会再次查询物品能力的 `applyEmptyingQuality`，防止递归。
- 返回空容器为干净的新栈，不残留酒的效果、品质或流体 NBT。生成的流体保留明确的流体身份数据；不将全部物品 NBT 任意复制为流体身份。
- 仅给明确登记且缺少适用原生能力的物品补齐，保留森罗、妖归等原生 handler。原有能力存在但与登记数据不一致时给出诊断，不强行覆盖。
- 能力附加与原生能力探测分开，不能在同一栈的能力构建回调中递归调用其能力初始化。验证标准 Forge 附加顺序及缓存行为，避免重复 provider 抢占。
- 首版不以单个物品 ID 覆盖部分装填瓶、NBT 决定多种内容的容器或已有多罐容器；此类物品继续走自身 handler 或酒桶配方后备。

## 二、KJS 接口与唯一内容来源

### 拟新增 API

在 CDC 增加 `compat/alcohol/ItemFluidContainers`，以简单参数提供 Java 静态入口，并通过现有 `global.CDStartupJavaClasses` startup facade 暴露为 `$ItemFluidContainers`。沿用已有 `AlcoholDrinks` 的 public static 调用方式，无需为这层数据接口新增 CDC 对 KubeJS 的编译依赖。

| API | 约定 |
|---|---|
| `register(itemId, fluidId, amount, emptyContainerId)` | 严格登记固定满瓶规则；非法 ID、非正液量或冲突重复定义报告配置错误 |
| `registerIfPresent(itemId, fluidId, amount, emptyContainerId)` | 用于现有含可选模组的内容清单；物品/流体/容器缺失时跳过并记录原因，参数错误仍报错 |

同一条规则重复登记可视为幂等；同一物品出现不同流体、容量或空容器时不能采用最后写入覆盖。Java API 不依赖 JS 回调来执行游戏运行时的 fill/drain。

拟在新增 startup 配置脚本中复用现有清单，结构如下，具体类尚待实现：

```js
// priority 低于 01_alcohol_drinks.js；示意，不是当前可执行接口。
global.CDAlcoholDrinks.forEach(drink => {
    global.CDStartupJavaClasses.$ItemFluidContainers.registerIfPresent(
        drink.item, drink.fluid, drink.amount, drink.container
    )
})
```

- `global.CDAlcoholDrinks` 仍是已有酒类物品、流体、容量和容器数据的来源；不另写一套六款对应表。颜色、醉酒效果等字段不影响流体能力。
- 已有能力的条目保留原实现并核对一致性。`global.CDTavernFermentedDrinks` 仅保留原玩法/品质陈酿职责，不作为能力登记或酒桶流体识别白名单。
- ID 数据在 startup 阶段收集，在注册表可用且世界开始使用前完成解析、校验和冻结；不能在自定义流体尚未注册时误判其缺失。
- 注册变更需完整重启，不声称 `/reload` 会给已构建能力的所有物品栈热替换 provider。验证启动期间提前建立的模板复制后可正确获得能力，旧存档加载出的新物品栈也应正常接入。
- 客户端和服务端加载同一份 startup 规则；不依赖某个存档先加载过 server recipes，避免界面查询与实际排液口径不同。

以后新增酒，正常补齐已有酒类清单即可自动登记能力；未加入清单但已有原生能力、emptying 或 filling 定义的酒桶配方，仍能通过下一节接入，不需要新增 Java 分支。

## 三、酒桶通用解析器，保留 emptying 与 filling 兜底

输入是配方实际组装出的成品、容器 `carrier` 和当前配方管理器；输出包含单份流体、单份 mB、原成品模板、允许容器和解析来源。

选择顺序为 **物品流体能力（包括 CDC 补齐的能力）→ 确定性 emptying → 可唯一反推的 filling → 既有 CGT 原生转换**。后备不要求前一级存在；可靠来源之间实际冲突时报告原因，不通过优先级掩盖冲突。

1. 复制为 `copyWithCount(1)`，原组装数量另记。能力读取、模拟以及用于验证的执行均在隔离副本上完成，不修改真实库存或共享配方模板。
2. 从 `FLUID_HANDLER_ITEM` 得到单一可排流体和实际液量，验证完整排液后的容器符合 `carrier`。读取实际内容，不把 tank 容量当成内容，也不设 1000mB 探测上限。
3. 无可靠能力时，读取匹配结果物品的确定性 Create emptying 定义，只接受单一流体、确定的液量及空容器，无概率结果或额外副产物。
4. 仍无法确定时，反查 Create filling：“一个空容器＋指定液量→一件目标成品”。只接受保证产出的单件成品，不能靠 `rollResults()` 猜测结果。**仅有 filling、没有 emptying 和物品能力，也必须支持。**
5. 原生 CGT 转换保留为后备。它只处理既有身份和变体，不向其目录插入外部物品，也不注册重复成品流体。
6. 全部来源均无法可靠推导时保留原物品模式，给出物品、配方 ID 和失败原因，不丢弃产物或凭名称猜酒液。

物品能力 provider 使用第二节的静态内容定义，不反过来调用酒桶解析器、`GenericItemEmptying` 或 filling 索引获取自身内容，避免“解析能力→反查配方→再次解析能力”的循环。

### filling 与转换一致性

- 比较目标物品 ID 和身份 NBT，仅归一化 QFF 明确桥接的品质字段；保留药效、饮品变体等身份区别。
- filling 的容器 ingredient 与酒桶 `carrier` 必须相容；保存交集作为该转换的允许容器，龙头仍需检查实际提供的空瓶。等价转换可保留多个合法容器选项。
- 从 `FillingRecipe.getRequiredFluid()`／`getFluidIngredients()` 获取 `FluidIngredient`，从 `getRequiredAmount()` 获取液量。支持具体流体和 tag，但 tag 存在多个不同流体身份时不能任取第一项；可用已确定的可靠来源进一步缩小候选。
- 同一物品的重复等价配方可以合并，仍存在不同流体、液量或不能解释的容器冲突时维持物品模式并列出候选 ID。只有 filling 时不自动生成逆向 emptying 配方。
- 按配方/tag 重载建立并失效索引，不逐 tick 扫描全部配方；缓存不跨不同物品 NBT 共用可变结果。已经开始的批次使用解析快照，不因重载换酒。

Create `6.0.8` 的 `GenericItemEmptying.emptyItem()` 是药水、配方、能力的处理顺序；其模拟分支也会 `rollResults()`，只取首个物品结果，能力排液还存在 1000mB 上限。因此解析器读取确定性定义，不简单调用该 helper 两次作为模拟和执行。

## 四、真实成品罐与统一出料

### 酿造和陈酿

- 保留输入 tank，另增专用成品 `FluidTank`。流体模式以罐内 mB 为唯一库存，不再同时保留可独立提取的成品物品或 CGT 零头 Map。
- 批次开始时保存解析快照、原成品模板、组装份数、单份量、容器约束和品质状态。总量为“原配方实际组装份数 × 单份液量”，用有界运算校验 4000mB 酒桶容量；超容量时保留原物品模式并诊断，不截断、扩容或暗改份数。
- 所有流体模式批次都等待配方 `unit_time`；初酿期间只有待产出记录，没有可抽酒液。初酿完成一次性生成成品流体并写 QFF 品质，模板仅用于显示及还原瓶装物品。
- 是否可陈酿沿用现有规则，通用能力不自动赋予任意液体陈酿/调酒资格。继续陈酿只更新桶内剩余酒的品质，已抽出部分不变化；普通出料不重掷品质或重置计时。
- 更新 `BarrelQualityMixin` 的空输出槽判断、完成写出和清理，显式区分物品模式与流体模式，避免流体罐尚有酒时旧逻辑提前重置，或又生成一份物品产物。

### 管道与 Forge/Create 接入

- 接管 CGT 成品可见性及抽液入口，流体模式直接委托真实成品罐，不再要求 `CGTDrinkCatalog`。保留多方块控制器解析、原允许接入面及 Forge/Create 查询路径，不附加竞争的第二份酒桶能力。
- 空闲时保留原输入行为；初酿未完成无成品可取，完成后支持任意 mB、两种 drain 重载及精确 NBT/品质匹配。
- 成品罐对外只排液，拒绝倒灌；模拟不修改状态。流体模式不再使用 CGT 静态 `VIRTUAL_DRAIN_REMAINDER`，所有零头自然保存在罐内。

### 水龙头、地面容器与置物台

- 保留当前批次的原成品单件模板和允许容器，龙头不需要全局反查“这个流体属于哪一瓶酒”。
- 先验证容器、完整单份液量和接收容量，再原子提交扣液、耗容器和交付。失败不扣料、不掉落溢出物，末瓶品质在清理批次前写入。
- 成品保留原物品 ID、效果和必要 NBT；品质由当前酒液写入。外部酒不增加森罗 `BrewLevel`；原生酒保持原有瓶器、变体和可放置容器行为。
- 覆盖原生开阀检查、`extractOneOutput`、放置容器、地面物品及 `TavernTapDepot`，全部使用统一出料服务，保留手动/红石开阀、堆叠空瓶及满缓冲恢复。
- 残液不足一瓶时龙头暂停，管道仍可抽取。4000mB 抽走 100mB 后再取 15 瓶，只剩 150mB，不能再得到第 16 瓶。

### 存档和显示

- 版本化保存实际流体/NBT、单份液量、原成品模板、容器约束、解析来源、模式及初酿/陈酿状态；排空时统一清理后再允许下一桶。
- 旧成品只在成功解析时一次性迁入成品罐，并清掉旧库存；失败维持原模式。初酿中在完成时转换，陈酿计时保留。旧版本静态 Map 已随重启丢失的历史零头无法无损还原，不能声称可以恢复。
- Jade、交互提示及适用液面渲染读取相同状态，显示实际 mB 和可装瓶数；不假填输入 tank，也不更改原开盖规则。

## 五、实施阶段和验收

1. **物品能力与 KJS 接口**：先做独立的固定满瓶 handler、登记校验、startup facade 和现有清单批量接入，验证返瓶及品质，不依赖酒桶改造才能工作。
2. **解析器与后备**：能力、emptying、filling、原生后备及冲突诊断；验证单份量和容器一致性。
3. **成品库存与存档**：完成时真实产液、陈酿、迁移、空槽判断及排空清理，禁止双库存。
4. **统一自动化出料**：CGT/Forge/Create、全部龙头分支、置物台和显示。
5. **回归与交付**：针对性 GameTest、Java 构建及 Mixin/refmap 检查；重启并确认加载新 JAR 后进行真实游戏测试。

| 验证对象 | 验收要求 |
|---|---|
| 旧酒瓶及新酒瓶的能力 | 无 `Fluid` NBT 仍显示正确满瓶；查询/模拟不改 NBT，复制和保存重进一致；两种 drain 正确 |
| 返瓶及整瓶语义 | 请求不足一份不排液，执行一次返回正确空瓶，重复查询不恢复满瓶；堆叠只处理分离的一件；成品瓶不能倒灌 |
| 原生 handler 与启动时序 | 森罗/妖归等能力不被替换；启动提前生成模板、旧存档栈、客户端/服务端一致；无能力初始化递归 |
| 配置校验 | 正/非法 ID、缺失可选模组、零/负容量、重复相同及冲突规则、注册表尚未就绪、新流体注册后校验 |
| 当前六款外部酒 | 苹果酒、紫颂果酒、三款魔法酒、恶魂烈酒：能力、管道、正确瓶器和效果，当前 16 份对应 4000mB |
| 四档品质 | 普通/铁/金/钻的能力排液、储罐运输、Create 重新装瓶及桶内陈酿一致，不出现能力递归或共享模板串品质 |
| 新增普通配方 | 不在原六款列表中，分别只有原生能力、CDC 登记能力、emptying、filling 四条路径，均不新增 Java 特判 |
| 仅 filling | 无物品能力且无 emptying，仍可酿造成流体、管道抽取、龙头及置物台取瓶；不强制新增能力登记 |
| 反推与歧义 | 成品 NBT、错误容器、唯一/多成员 tag、等价重复、不同流体/液量冲突、概率/多产物/批量结果，不随意取第一项 |
| 不同单份量与小量抽液 | 100/500mB 等合法单份量；1/50/100/249/250/1000mB 连续抽液、超量请求、NBT不匹配及堵塞，不复制或丢酒 |
| 混用出料 | 抽 100mB、取 15 瓶后剩 150mB，只能继续抽残液；主/代理部件、允许面、手动/红石和满缓冲恢复正确 |
| 批次与存档 | 残液、初酿中、陈酿中、旧物品库存、重载/tag变化、区块卸载及重启均不重复转换或换批串数据 |
| 单一库存 | 流体模式无法再经旧输出槽、原生出瓶或 CGT 虚拟成品提取第二份库存；非流体模式可正常取物品 |

既有 GameTest 曾在 Mixin 配置资源读取阶段启动失败，实施时先排除测试启动问题，编译不等于行为测试通过。CDC 改动走 Core PR；正式更新父包指针和打包 JAR 时，按 `cdc-bump`、`packwiz-assets` 流程引用已合入 `1.20.1` 的提交。

## 主要实现入口和维护边界

- CDC 拟新增：`compat/alcohol/ItemFluidContainers` 及 provider/固定满瓶 handler；`compat/kaleidoscopetavern/` 下的通用解析器、成品库存与统一出料服务。
- 既有 CDC：`TavernBarrelAccess`、`TavernBarrelBatch`、`TavernQuality`、`TavernTapDepot` 及对应 `BarrelQualityMixin`、`BarrelTapDepotMixin`、`DrinkFluidConversionsMixin`、`BarrelJadeMixin`；Java 注册入口按本模块 AGENTS 执行。
- KJS 拟改：`startup_scripts/00_java_classes.js` 增加 facade，新增能力登记 startup 脚本，复用 `01_alcohol_drinks.js` 数据。现有 `Alcohol/{production,recipes}.js` 继续配置生产及装排液，不实现运行时 handler。
